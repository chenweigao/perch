## 选题与假设

- 来源：round-25 评估轮评审 F7 指认"跨实例缓存保真"方向（StreamingBench 前序查询已渲染
  窗口，缓存准入/容量允许时 coldFind 首项也可能不冷），叠加 round-16 归因：一次冷查询
  ~80% 花在渲染（link detection 66.6% + parse 14%），匹配只占小头。
- 产品形态：find bar 每次打开都新建 `ConversationSearch`（workspace 历史搜索在每次
  **显式执行的搜索**中按匹配会话新建实例——UnifiedSearchView 在查询变化时取消在途搜索、
  不做每击键重搜；评审 F3 更正后的准确对应面），每个新实例把可搜索窗口的全部 source
  重新走 `ReplyDocument.parse + renderedText`。同一进程内这些渲染结果只依赖 source 的
  精确 UTF-8 字节（见设计论证第 1 点），跨实例共享后：重开的 find bar / 重复的显式历史
  搜索只付匹配、查表与 Entry 构建，不再付渲染。
- 队列门控："不得引入全局 memo"（INDEX 红线）要求有界缓存给出设计论证——本节下述五点
  即论证，全部有钉死或机制说明支撑。
- 单一假设最小修改：产品侧仅 1 个新文件（`RenderedSourceCache.swift`）+ `ConversationSearch`
  的 init 注入与渲染行改写；`Sources/AgentWorkbench` 零差异（默认参数使所有既有调用点不变）。

## 设计论证（队列门控要求）

1. **纯函数性（限定环境假设下——评审 F7 收窄）**：`renderedText(ReplyDocument.parse(source))`
   在进程内是 source 精确字节的确定函数——parse 管线确定性，link detection 走 ReplyDocument
   的进程级 `static let` NSDataDetector。static 只证明检测器**构造一次**；其 `matches` 不
   咨询运行期可变 locale 是**平台语义假设**而非 static 本身可证——且链接状态参与 ReplyMath
   的数学拆分准入（检测器行为并非与渲染文本无关），第 4 点的 locale 世代正是对该假设的
   纵深防御界定。round-12 实例内复用依赖的是同一 **UTF-8 保真**契约（引用范围仅限保真，
   不构成检测器/locale 稳定性的额外证明）。评审方 Linux 原生扩展检查（0B 无缓存参考端、
   3,360 次 oracle 调用、10,080 次逐字节全字段比较零失配，40 窗口×6 查询×7 选项组×running
   双向×shared/fresh/512B 制度）支持实现，不冒充 Mac 全环境证明。
2. **字节精确键，绝不用规范键**：规范相等但编码不同的 source（NFC/NFD 载荷互换）渲染出
   **不同**的搜索字节（round-12 `sameRenderedUTF8` 推理），`Dictionary<String, …>` 的规范
   相等键会合并两者并返回错误渲染。键 = 精确 UTF-8 字节数组，逐字节哈希与比较。
3. **有界**：总成本 = **渲染 UTF-16 码元数 ×2 + 键 UTF-8 字节数**（成本**估计**而非精确
   RSS，与 native math 缓存准入估计同一约定），上限 `byteBudget`（默认 32 MiB）。评审
   独立重放 16k 消息 bench 窗口冷遍的估计分解：渲染 4,399,434B + 键 3,150,941B =
   **7,550,375B = 32MiB 的 22.501871%**（评审 F10：7.55MB 是渲染+键的合计估计，既非单独
   "渲染大小"、更不是 RSS）。溢出批量 LRU 驱逐——**诚实成本说明（评审 F9）**：驱逐恰好
   降到预算即停、无低水位余量，满表持续 churn 时每次插入都付锁内 O(N log N) 全表排序
   （评审探针：2,048B 预算、9B 条目、500 唯一插入 → 273 次排序）；低水位/侵入式 LRU
   链表可消除该成本但改变驱逐语义、需重新验证——本轮有意不做。单条渲染成本超整个预算的
   病态载荷照常渲染但**不入表**（不能搅动表）。
4. **locale 世代**：产品的 NSDataDetector 是进程级 static，行为在创建时固定；作为对任何
   匹配期 locale 咨询的纵深防御，`NSLocale.currentLocaleDidChangeNotification` 观察者递增
   世代并整表丢弃。缓存不持有 session/UI/连接引用、不超出进程生命周期（state-and-effects
   纪律：与页面、窗口生命周期无关）。
5. **线程安全**：find bar 搜索在主 actor，历史搜索在后台。一把锁护表；`produce` 在锁**外**
   执行（渲染跑 cmark + Data Detectors，持锁渲染会把独立搜索串行化）。同一 source 的并发
   miss 可能渲染两次——两次都是同一纯值，后写者胜，良性（钉死的并发烟测只断言值正确，
   不断言不重复渲染）。

注入方式：`public init(renderedCache: RenderedSourceCache = .shared)`——默认参数保持全部
既有调用点（含 AgentWorkbench）逐字节不变；需要观察真冷渲染的基准/测试注入新实例。

## 归因探针与方法论修正（v1→v2 的证据）

Linux 粗筛 v1 出现预期外信号：`find_bar_cold_query` 基线 551ms vs 候选 350ms（-36%），
而该指标按 v1 声称应当语义不变。归因探针（**探针专用二进制，绝不用于采纳数**；补丁与
输出归档 `round-27/probe/`）：

- 方法：RenderedSourceCache 加每实例 produce/hit 计数器（探针 only）；两侧 bench 冷循环加
  同实例二次调用计时；双二进制交替 2 轮。
- 结果：候选每个冷遍 `produce=963 hit=17253 bytes=7,550,375`（评审独立重放确认：2 runs × 5 cold = 10 组计数逐位相同）；基线
  冷遍 553-560ms、二次调用 0.16ms（round-12 Entry 缓存复用路径——它跳过渲染**和**匹配，
  不能当"匹配成本"引用）。
- 解释：bench 夹具每个 turn 由同一组模板串构造（thinking/prompt/answer/readOutput/
  bashOutput/grepOutput/oldBlock/newBlock/written 跨全部 turn 重复；cold 窗口=230 完成轮+1 running 轮=231 轮，另有 5 个 earlier 分页轮同构，235 是完成轮总数——评审 F10 计数范围更正），16,142 消息
  窗口的 18,216 个 source 出现塌缩为 963 个唯一值（94.7% 重复）。缓存前代码对每次出现
  重渲染；缓存把同遍重复去重——**-36% 是真实产品行为（去重），份额被夹具放大**。
- 收益分解（同一候选二进制内）：渲染 963 个唯一源 ≈ cold − reopen = 350.89 − 229.34 ≈
  121.6ms（Linux）；reopen 跳过全部渲染。真实语料的重复率依语料而定（重复的相同工具输出/
  重复读取的相同文件确实存在，但不会到 94.7%），报告把**跨实例复用（重开/重复显式
  搜索）作为首要产品主张**，同遍去重作为第二机制并如实标注夹具放大。
- v2 修正：bench 两处注释重写（不再声称语义完全不变；写明去重效应与分解位置）、
  产品 doc 增补同遍去重说明、钉死语料增加重复 source（下节）。

## 行为等价钉死（checkRenderedSourceCache，新；v3 版=评审 F1/F2 处置后）

- **Part 1 机制**：produce-once；NFC/NFD 字节精确键（produce 调用序列钉死）；**精确成本
  记账**（estimatedByteCount == 渲染 UTF-16 码元×2 + 键 UTF-8 字节，逐值断言）；
  **具体 LRU**（预算 12B 装两个 6B 条目 → touch A → 插 C：B 必须被逐且再 produce，A/C
  必须零 produce 留存——LRU 排序反向的变异体当场死）；**超大载荷对非空表**（哨兵条目
  在位时 cost≫预算的载荷照常渲染、记账不变、哨兵零 produce 留存——先入表后驱逐的变异体

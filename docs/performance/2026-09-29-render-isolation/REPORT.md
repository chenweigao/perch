# 首次行渲染与整体瓶颈诊断

本轮的主要成本在界面图更新和布局。正文冷宿主测量是其中一部分，但不足以解释
整体切换耗时。下一步优先试验稳定的会话页面宿主和更小的目录更新边界；继续使用
Observation + Swift Concurrency + SwiftUI/AppKit。暂不因本次数据引入 TCA、SwiftData
或更大的行宿主缓存。

本轮只增加编译期开关下的诊断探针、独立场景和采样归类，没有改变生产渲染策略。
这是同一二进制的场景拆分，不是优化前后的 A/B，也不是应用冷启动测试。

## 三种独立场景

Apple M4、16 GiB、macOS 27、Swift 6.4、release -O，窗口 1280×820。
每个独立进程先挂载 session-0，等待两秒，然后执行 80 步。固定目录有 500 条数据，
最近会话实际最多显示 20 条；联合/目录场景交替显示 0 或 4 条置顶记录。
八个驻留会话各有 200 轮富文本历史，正文仍只挂载可见行。

| 场景 | 三轮中位数的中位数 | 各轮中位数范围 | 各轮 p95 范围 |
| --- | ---: | ---: | ---: |
| 切换会话与草稿，目录固定 | 52.84ms | 52.84–53.53ms | 58.46–60.64ms |
| 更新目录状态、顺序、置顶，会话固定 | 25.40ms | 24.72–25.82ms | 32.05–39.35ms |
| 同时切换与更新目录 | 73.77ms | 73.44–74.83ms | 83.23–89.96ms |

三轮按不同顺序串行执行：切换→目录→联合、联合→目录→切换、目录→切换→联合。
计时期间没有本任务的编译或 profiler；其他桌面进程不受控制。各场景的耗时不能
相加来推算联合耗时，也不能把联合与纯切换的差值当作侧边栏的独占成本。

计时从模型修改前开始，到 layout/display/CA flush 后，确认挂载的侧边栏投影、
选中的正文和草稿均正确。每步构造 fixture 数组在计时外，投影检查和视图树检查在
计时内；目录场景仅第一步设置固定草稿。终点不包含屏幕实际显示时刻。独立 CPU
区间覆盖完整循环，因此包含 fixture 数组构造。旧 `switching` 模式保持原样；它的
计时起点较晚，不能直接与新场景做优化 A/B。

## 首次渲染和测量

切换场景每轮创建 320 个行宿主，首次测量 320 次，重测 0 次，即每次切换四个冷宿主。
这里的“冷”指新 UI 宿主；进程内的解析、字体等缓存可能已经热了。

以纯切换三轮为例：

| 阶段 | 每轮 80 步合计 | 含义 |
| --- | ---: | --- |
| 宿主控制器初始化 | 15.10–15.50ms | 构造对象，不等于完成 SwiftUI 图创建 |
| 首次 `sizeThatFits` | 481.54–490.15ms | 平均每次切换约 6.0–6.1ms |
| 用户行首次测量 | 88.00–89.41ms / 160 行 | 平均每行约 0.55–0.56ms |
| 回复行首次测量 | 393.73–400.95ms / 160 行 | 平均每行约 2.46–2.51ms |
| Markdown 解析 | 47.70–48.16ms | 每次切换约 0.60ms |
| 原生文本测量 | 39.15–39.71ms | 每次切换约 0.49ms |

这些阶段嵌套，不能相加。`sizeThatFits` 会触发更深的视图/文本工作；后续异步
图更新和布局也不都包含在它里面。不能用 15ms 的初始化阶段声称创建 UI 很便宜，
也不能把 6ms 当成整条正文渲染管线的总成本。

640 次 attach 拆成 320 次首次挂载和 320 次重新挂载，而非创建了 640 个宿主。
重新挂载合计约 18ms/轮，没有再次触发 `sizeThatFits`。本轮未进一步定位每次移除
与重新挂载的触发者；该同步阶段约 0.23ms/次切换，不是当前首要优化对象。
固定会话的目录场景没有正文内容协调、宿主创建、测量或 Markdown 解析记录。

## 独立 CPU 采样

每个场景另采样一次，用 `RenderIsolation` signpost 限定半开区间，排除启动、
等待和后续滚动。新增的分类按以下优先级每个样本只计一次，列相加等于主线程总权重。

| 主线程采样上下文 | 只切换 | 只更新目录 | 联合 |
| --- | ---: | ---: | ---: |
| 行 `measure` 栈 | 481ms | 0ms | 480ms |
| 行初始化栈 | 22ms | 0ms | 14ms |
| 其他正文相关栈 | 304ms | 1ms | 308ms |
| 侧边栏相关栈 | 23ms | 157ms | 150ms |
| 输入区相关栈 | 244ms | 1ms | 249ms |
| 剩余 AttributeGraph 更新栈 | 1325ms | 1015ms | 2225ms |
| 剩余 AppKit 布局栈 | 937ms | 509ms | 1376ms |
| 其他 | 988ms | 340ms | 1188ms |
| **总计** | **4324ms** | **2023ms** | **5990ms** |

联合场景的行测量约占 8.0%；纯切换约占 11.1%。扣除已归类的同步应用栈后，联合
仍有约 60.1% 在框架图更新/布局上下文，纯切换约 52.3%。这些是采样 CPU，不是墙钟
占比或 FPS。框架延后执行的工作通常没有原始功能调用者，不能把“剩余”全算给
侧边栏或正文；侧边栏 150ms 也绝不代表其总成本只有 150ms。

三个场景共同说明：目录 UI 更新有独立成本；目录固定时仍有较大的会话切换成本；
优先优化数据投影或 Markdown 解析无法覆盖主要采样热点。更精确的控件级归属还需要
SwiftUI Instruments 的因果图或小范围对照实现。

## 架构决定与下一步

1. **先试验稳定的会话详情宿主。** 当前 `NativeConversationState.select` 清空 snapshot，
   `NativeAgentView` 按有无 snapshot 切换正文/加载分支，输入区另有 `.id(s.id)`。
   CPU 栈也出现正文 dismantle、宿主回收、输入框创建和 toolbar 布局。这提供了具体的
   生命周期调查入口，但尚未证明消除某一个分支能节省多少时间。
   下一步把“选中了哪个会话、加载状态、可展示数据”与渲染宿主的生命期分开，保留稳定
   容器，以明确的会话上下文更新内容。必须禁止加载期间把旧正文标成新会话，也不能
   直接删除 `.id` 而让草稿、撤销栈、组字、焦点或回调串到另一会话。
2. **目录按可见投影和行 ID 更新。** 保留现有最多 20 条最近记录的策略，进一步分开
   selection、单行状态、顺序/分区结构的变化；先减少不变内容的失效和不必要的尺寸
   更新。若可见目录仍占显著成本，再对照试验 AppKit 列表复用，保留原生玻璃、hover、
   键盘及可访问性。不能仅因底层目录有 500 条就直接换列表框架。
3. **正文继续采用现有 AppKit 可见行挂载与显式测量。** 先保留内容/视口分离和有预算
   的展示模型缓存。跨会话复用 SwiftUI 行宿主会引入环境、展开状态和内存失效契约，
   当前 6ms 同步测量成本不足以支持优先扩大该缓存。
4. **框架服务于问题。** Observation + Swift Concurrency 继续管理状态与任务边界；
   TCA 可在多步异步流程中验证组合和测试收益，本次未做 TCA 性能对照。SwiftData
   等到持久化查询成为实测问题再考虑。Markdown 后台化也等到解析成为热点。

下一轮仍用这三个场景做同条件 A/B，另验草稿/组字、旧响应丢弃、阅读锚点、分页、
焦点和持续更新内存。新架构的采用条件是这些契约通过，且响应或 CPU 有稳定收益；
本报告没有声称已经获得该收益。

以上方向与 Apple 关于视图依赖、身份和生命周期的说明一致：
[SwiftUI 性能](https://developer.apple.com/videos/play/wwdc2023/10160/)、
[Instruments 因果分析](https://developer.apple.com/videos/play/wwdc2025/306/)。
[TCA 官方说明](https://github.com/pointfreeco/swift-composable-architecture)侧重状态、组合、
副作用与测试；不能据此推导它会消除 Perch 的布局热点。

## 复现与边界

```sh
scripts/build-native-acceptance.sh
python3 scripts/run-native-acceptance.py --mode render-switching --output <新目录>
python3 scripts/run-native-acceptance.py --mode render-catalog --output <新目录>
python3 scripts/run-native-acceptance.py --mode render-combined --output <新目录>
```

使用 `--app <保存的应用>` 固定二进制；独立采样增加 `--capture cpu`。从导出的
`os-signpost.xml` 取目标 PID 的 `RenderIsolation` 边界，再给
`summarize-time-profile.py` 传 `--after` / `--before`。分类的守恒、嵌套优先级、
后台线程排除和半开区间有 Python 检查。

逐轮耗时、阶段计数、采样分类、编译器和源码/二进制摘要见
[measurements.json](measurements.json)。原始记录和固定应用保存在工作树
`.local/render-isolation/`。基于 `21f31dc` 加诊断改动，构建清单中的 commit 是父提交，
精确来源以 source_sha256 和 binary_sha256 为准。

九次无采样运行、三次 CPU 采样及原有 native `all` 挂载/内容协调检查通过；生产
`scripts/build.sh`、WorkbenchChecks 和 19 项 Python 测量工具检查通过。没有推送、
部署或运行真实 SSH 检查。

这是本机离线挂载实验，不覆盖真实 SSH、模型、硬件键盘、真实输入法、显示延迟或
长期使用的 FPS。目录场景是集中改变状态、顺序、置顶的压力输入，不代表常态轮询。

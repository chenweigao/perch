# 渲染架构的体验门槛

以下是本次工作的工程目标，不是 Apple 的认证标准，也不是已通过的结论。
先冻结指标，再查看 A/B；不因某个候选恰好落在某个值上临时放宽门槛。

| 指标 | 暂定目标 | 测量边界 |
| --- | --- | --- |
| 本地会话切换 p95 | ≤100ms | 已驻留数据、模型变化至正文/草稿与布局就绪，单列网络等待 |
| 输入提交 p95 | ≤16ms | 原生输入控件至 draft 和布局就绪；不包含物理键盘和显示器 |
| 持续更新的主线程调度延迟 | p99≤16ms；额外延迟>50ms 的次数逐次报告 | 每10ms主线程任务唤醒的迟到量，包含 OS 调度，不是帧率 |
| 阅读锚点 | 非主动滚动时漂移≤1pt | 流式更新、输入及切换返回；不丢 entry 身份 |
| 输入正确性 | 丢字/重复提交/组字串会话为0 | 原生输入协议自动验收；真实输入法候选窗另验 |
| 长时资源 | 无持续增长的保留行/任务队列 | 30秒实验只能筛明显异常，10分钟真实使用仍需补证 |
| 显示流畅度 | 有效应用帧事件与正向控制后才评判 | 缺少有效帧事件是未验证，不是零卡顿 |

候选采用要求：目标操作的 median 和 p95 均稳定改善至少15%；普通切换、输入和持续
更新无稳定超过5%的回退；内容、操作、滚动、焦点、hover、可访问性与外观契约通过。
帧和真实输入证据缺失时，不声称整体体验已达标。

## 正向控制

AcceptanceResponsiveness 每10ms在主线程恢复一次，记录超出预期唤醒时刻的延迟。
`--responsiveness-control` 在采样启动后插入80ms主线程停顿；必须检测到≥70ms。
该运行用于验证测量器，不能混入候选的普通性能统计。计时结束立即取消采样任务。
InputAcceptance 原有80ms输入正向控制单独验证输入边界。二者都不替代显示帧控制。

## 对照范围

- `flat`：正式使用的同一 ForEach 稳定行 ID。
- `table`：仅验收程序启用 NSTableView，使用相同投影、SwiftUI行内容和业务操作。
  按 ID 插入/移动/删除，复用可见单元；会话 ID 变化重置 cell 内 SwiftUI 状态。
- 两者共享业务状态、正文及 composer。渲染容器不同，不能要求虚拟化列表创建所有
  屏幕外行。table 的布局验收核对完整数据顺序和可见行值/顺序/高度，并实际滚动
  到底部再返回顶部核对复用内容。表格几何计数仅覆盖挂载探针，不与 eager 全量相减。
- 原型使用当前字号对应的分区/尾部高度，并保留 SwiftUI 的每行 hosting；因此其结果
  只证明这个混合实现，不代表纯 AppKit 行渲染的性能上限，也不自动满足完整交互契约。

真实应用观察与 A/B 分开记录，必须核对运行二进制来源。未经同构建、同负载复测，
不得把已安装版本的体感或 CPU 样本归入候选的性能提升。

# Round 9：长单轮状态栏派生免中间数组（2026-11-13）

产品基线 `e160eec`（#328，round 8 已合并）。单一假设：一个长时间自主执行的单轮里，
状态栏每次更新都重建 `ConversationActivity`，而它为了列出工具与计划，先把整轮消息和
整轮的每个 part 物化成若干临时数组。

## 归因

- 场景成本随**当前轮长度**线性增长，而不是随消息数：Linux 单轮 400 条 0.497ms、
  2,000 条 2.484ms；Mac 0.3455ms / 1.6545ms。同样 6,400 条消息分成 1,000 轮时，
  同一构造只要 0.007–0.012ms。
- perf（`WORKBENCH_BENCH=activity`，新基线）：`ConversationActivity.init` 占全进程
  children 6.08%，其中 `ToolVisibilityProjection.project` 3.67%、
  `ConversationTodo.floating` 1.14%、`KimiPart` 的 destroy/copy/WOc 合计约 3%；
  fixture 构造占 72.10%，嵌套比例不可相加，也不是 A/B。
- 走读定位到三处纯机械拷贝：
  1. `let current = Array(messages.dropFirst(start))`——`start == 0`（整窗就是一个长轮）
     时把整个窗口复制一份；
  2. `projection.messages.flatMap(\.content).filter { $0.type == "tool_use" }.compactMap { … }`
     ——先物化本轮**所有** part（`KimiPart` 184 字节且带引用计数字段），再物化其中的
     tool_use，最后才得到可见工具；
  3. `ConversationTodo.floating` 再 `Array(messages[start...])` 复制一次，`current(in:)`
     里两次 `messages.flatMap(\.content)`（其中一次还先 filter 出全部 tool_result），
     合计三份 part 数组。

## 产品修改

- `ConversationActivity.init`：`start == 0 ? messages : Array(messages.dropFirst(start))`；
  可见工具改为按源顺序单次遍历（消息 → part → `projection.tools[id]`），不再物化 part。
- `ConversationTodo`：`floating` 把 `ArraySlice` 直接交给新的私有 `current(in:)`，公开的
  `current(in: [KimiMessage])` 转调它；两个 `flatMap(\.content)` 换成嵌套遍历。
  结果字典仍按同样顺序覆盖，TodoList 仍取最后一个完整成功的写入。
- 顺序、重复 id、孤儿结果、`is_error` 结果、未成功的 TodoList 写入与轮边界语义逐条不变。
  `Sources/AgentWorkbench` 零差异；无新缓存、全局状态、异步/连接/权限或 UI 修改。

## 行为等价检查

- 新增一条断言把可见工具的**顺序**钉死：
  `mixed.tools.map(\.id) == ["t", "returned", "failed", "missing", "active", "plan"]`
  （覆盖去重后的重复调用、无结果、有结果、运行中与 TodoList 写入）。该断言在
  **产品代码未改**的匹配基线构建上同样通过（91 PASS + 1 SKIP），说明它钉的是既有行为，
  不是为候选定制。
- 既有覆盖全绿：`checkConversationTodos`（写入/查询/失败/清空/轮边界/浮动列表生命周期）、
  `checkConversationActivity`（live/history 去重、结果优先、断连、审批、停止、轮隔离）、
  `ConversationTodo.current` 的另两个调用方（task context、task recap）相关检查、
  round 8 的 `checkWindowIdentityReuse` 与 90 步随机翻页检查。

## 结论

**采纳（以 Mac 为准）**：长时间自主单轮的状态栏派生 1.6545→1.2180ms（-26.38%）@2,000 条、
0.3455→0.2580ms（-25.33%）@400 条；轮越长收益越大，多轮窗口本来只有几微秒、无变化。
剩余大头是 `ToolVisibilityProjection` 为状态栏重建整轮 normalized 消息（perf children 3.67%），
留给下一轮，本轮不主张。

## CI math 门槛：三次失败与静机复测（未合并前的处置）

同一个 head `04e00ed` 在 GitHub 共享 runner（`cpu_count: 3`）上连跑三次 `math-performance`
都失败，但**每次失败的门槛不同、每次构建出的二进制 hash 也都不同**（基线
356fc3d3/b361b5f9/70808825，候选 36e07bd0/8de898df/c01e0137）：

| 门槛 | attempt 1 | attempt 2 | attempt 3 | Mac mini 静机 |
| --- | --- | --- | --- | --- |
| `parse_unclosed_4096` ≤1.25 | **1.328 失败** | 1.106 通过 | **1.365 失败** | 0.993 通过 |
| typeset-32 best-of-3 ≤1.15 | **1.507 失败** | **1.157 失败** | **1.620 失败** | 1.131 通过 |
| typeset-128 best-of-3 ≤1.15 | **1.450 失败** | **1.275 失败** | **1.294 失败** | 1.010 通过 |
| typeset-512（不设门槛） | 1.154 | 1.403 | 1.089 | 0.991 |
| 未设门槛的 parse 指标区间 | 0.90–1.99 | 0.82–1.71 | 1.08–1.60 | 0.97–1.00 |

Mac mini 静机复测用的是**同一个脚本、同一 6 轮 B,C,C,B,B,C 顺序、同一门槛**，工作树检出到
已提交的 `04e00ed`（`git archive HEAD` 因此与 CI 同源）、`WORKBENCH_MATH_BASELINE_REF=e160eec`，
结果 `status: passed`、`relative_performance_gates: applied`，全部比值 0.97–1.13。
该检查自己的语义门（baseline/candidate 解析语义一致）三次都先通过；本轮 diff 只改
`ConversationActivity.init` 与 `ConversationTodo`，数学预览的计时路径不调用它们。
证据：[math-gate-investigation.json](round-9/ci/math-gate-investigation.json)、
[initial-math-failure.json](round-9/ci/initial-math-failure.json)、
[initial-host-failure.json](round-9/ci/initial-host-failure.json)。

判定：CI 上被卡的是 3 CPU 共享 runner 上约 40ms 量级的 best-of-3，且每次尝试的二进制都不同
（布局也随每次构建变化），三次结果彼此矛盾；静机同口径全绿。**没有修改任何门槛、阈值或断言**，
处置是把证据提交上来换一个新 head 重跑 CI；若新 head 仍红，就按循环规则留 PR 不合并、
注明原因，主循环继续（第 10 轮从 `e160eec` 开），并把"math 输入指纹覆盖整个 WorkbenchCore，
使任何 Core 改动都被共享 runner 噪声门槛卡住"这一根因交用户决定，不自行改门槛适用范围。

attempt 1 的 `Native host lifecycle regression` 失败（`task-context` 阶段
`abs(reading.overviewOffset - 600) <= 2`）已在 Mac mini 上对候选与未改产品代码的基线各跑一次，
两边都 PASS（26.13s / 25.89s），attempt 2、3 该作业也都通过，按 runner GUI 时序抖动记录。

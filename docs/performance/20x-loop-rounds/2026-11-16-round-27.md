## 选题与假设

- 来源：round-25 评估轮评审 F7 指认"跨实例缓存保真"方向（StreamingBench 前序查询已渲染
  窗口，缓存准入/容量允许时 coldFind 首项也可能不冷），叠加 round-16 归因：一次冷查询
  ~80% 花在渲染（link detection 66.6% + parse 14%），匹配只占小头。
- 产品形态：find bar 每次打开都新建 `ConversationSearch`（workspace 历史搜索每次击键也
  新建），每个新实例把可搜索窗口的全部 source 重新走 `ReplyDocument.parse + renderedText`。
  同一进程内这些渲染结果只依赖 source 的精确 UTF-8 字节（见设计论证第 1 点），跨实例共享
  后：重开的 find bar / 连续击键的历史搜索只付匹配与 Entry 构建，不再付渲染。
- 队列门控："不得引入全局 memo"（INDEX 红线）要求有界缓存给出设计论证——本节下述五点
  即论证，全部有钉死或机制说明支撑。
- 单一假设最小修改：产品侧仅 1 个新文件（`RenderedSourceCache.swift`）+ `ConversationSearch`
  的 init 注入与渲染行改写；`Sources/AgentWorkbench` 零差异（默认参数使所有既有调用点不变）。

## 设计论证（队列门控要求）

1. **纯函数性**：`renderedText(ReplyDocument.parse(source))` 在进程内是 source 精确字节的
   确定函数——parse 管线确定性，link detection 走 ReplyDocument 的进程级 `static let`
   NSDataDetector（首次使用时固定）。内容寻址查表返回的值与重渲染逐字节相同；这正是
   round-12 实例内 rendered-text 复用已依赖的同一纯度契约。
2. **字节精确键，绝不用规范键**：规范相等但编码不同的 source（NFC/NFD 载荷互换）渲染出
   **不同**的搜索字节（round-12 `sameRenderedUTF8` 推理），`Dictionary<String, …>` 的规范
   相等键会合并两者并返回错误渲染。键 = 精确 UTF-8 字节数组，逐字节哈希与比较。
3. **有界**：总成本（渲染 UTF-16 字节 ×2 + 键字节——成本**估计**而非精确 RSS，与 native
   math 缓存准入估计同一约定）上限 `byteBudget`（默认 32 MiB：16k 消息 bench 窗口渲染后
   ~7.5 MB，预算覆盖数倍大转录同时封住最坏情况）；溢出批量 LRU 驱逐；单条渲染成本超整个
   预算的病态载荷照常渲染但**不入表**（不能搅动表）。
4. **locale 世代**：产品的 NSDataDetector 是进程级 static，行为在创建时固定；作为对任何
   匹配期 locale 咨询的纵深防御，`NSLocale.currentLocaleDidChangeNotification` 观察者递增
   世代并整表丢弃。缓存不持有 session/UI/连接引用、不超出进程生命周期（state-and-effects
   纪律：与页面、窗口生命周期无关）。
5. **线程安全**：find bar 搜索在主 actor，历史搜索在后台。一把锁护表；`produce` 在锁**外**
   执行（渲染跑 cmark + Data Detectors，持锁渲染会把独立搜索串行化）。同一 source 的并发
   miss 可能渲染两次——两次都是同一纯值，后写者胜，良性（钉死的并发烟测只断言值正确，
   不断言不重复渲染）。

注入方式：`public init(renderedCache: RenderedSourceCache = .shared)`——默认参数保持全部
既有调用点（含 AgentWorkbench）逐字节不变；需要观察真冷渲染的基准/测试注入新实例。

## 归因探针与方法论修正（v1→v2 的证据）

Linux 粗筛 v1 出现预期外信号：`find_bar_cold_query` 基线 551ms vs 候选 350ms（-36%），
而该指标按 v1 声称应当语义不变。归因探针（**探针专用二进制，绝不用于采纳数**；补丁与
输出归档 `round-27/probe/`）：

- 方法：RenderedSourceCache 加每实例 produce/hit 计数器（探针 only）；两侧 bench 冷循环加
  同实例二次调用计时；双二进制交替 2 轮。
- 结果：候选每个冷遍 `produce=963 hit=17253 bytes=7,550,375`（三轮迭代逐位一致）；基线
  冷遍 553-560ms、二次调用 0.16ms（round-12 Entry 缓存复用路径——它跳过渲染**和**匹配，
  不能当"匹配成本"引用）。
- 解释：bench 夹具每个 turn 由同一组模板串构造（thinking/prompt/answer/readOutput/
  bashOutput/grepOutput/oldBlock/newBlock/written 在全部 235 个 turn 重复），16,142 消息
  窗口的 18,216 个 source 出现塌缩为 963 个唯一值（94.7% 重复）。缓存前代码对每次出现
  重渲染；缓存把同遍重复去重——**-36% 是真实产品行为（去重），份额被夹具放大**。
- 收益分解（同一候选二进制内）：渲染 963 个唯一源 ≈ cold − reopen = 350.89 − 229.34 ≈
  121.6ms（Linux）；reopen 跳过全部渲染。真实语料的重复率依语料而定（重复的相同工具输出/
  重复读取的相同文件确实存在，但不会到 94.7%），报告把**跨实例复用（重开/击键）作为
  首要产品主张**，同遍去重作为第二机制并如实标注夹具放大。
- v2 修正：bench 两处注释重写（不再声称语义完全不变；写明去重效应与分解位置）、
  产品 doc 增补同遍去重说明、钉死语料增加重复 source（下节）。

## 行为等价钉死（checkRenderedSourceCache，新）

- **Part 1 机制**：produce-once（第二次查表不再调 produce、返回存量值）；NFC/NFD 字节
  精确键（规范相等的两条 source 是**两个**条目，produce 调用序列钉死）；512B 预算下
  200 源搅动的驱逐正确性（每次查表值正确 + 预算不破）；超大单源拒绝入表且每次重产；
  removeAll；8×200 并发烟测（并行 miss 下值全部正确；重复渲染按设计良性、不作断言）。
- **Part 2 端到端纯度（公开 find-bar API）**：语料含 NFC/NFD 同文变体（键合并缺陷会改变
  结果）、URL/代码/数学（ReplyDocument.parse 各路径）、**字节级重复 source**（v2 新增：
  a1 的第二个 text 部件与 a0 的回答逐字节相同——同遍去重路径的 e2e 钉死）。六个查询 ×
  三种缓存制度（shared 冷、fresh、shared 温）`ConversationFindResults` 全等；非空断言防
  空转；v2 追加：重复文本必须贡献**自己的** occurrence（≥3 hits）且两个 turn 条目都有
  命中（≥2 entryID）——去重若破坏 joined text 偏移，occurrence/excerpt 会漂移。
- 这是 round-12 warm-vs-fresh 复用不变量的缓存类比。Linux v2：checks 106 PASS + 1 SKIP；
  Mac v1 作业：base（旧钉死集）106 PASS、cand 107 PASS（Mac 多跑 math 渲染项）。

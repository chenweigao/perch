# Round 8：复用窗口按副本字节比较（2026-11-13）

产品基线 `ad4cb18`（#327，round 7 已合并）。单一假设：每个流式 delta 都要确认
"最新提示之前的窗口没有变"，而这次确认用 `elementsEqual` 逐元素走迭代器，
每一步都会拷贝一个 `KimiMessage`（retain/release 它的字符串与 parts）。改为对
未变副本按字节比较。

## 归因（round 7 代码，Linux perf）

- 采样调用图：`swift_retain` 占全进程 16.01%，其中 `KimiMessage` 值拷贝 4.08%
  → `elementsEqual(ArraySlice<KimiMessage>)` 2.06% → `ToolVisibilityProjection.canReuse`
  1.25%（`ConversationPresentationModel.update` 0.70%、`ConversationPresentationHandle.update`
  0.55%），另有 0.53% 从 `ConversationSearch.hits` 进入同一个 `elementsEqual`。
  百分比含 fixture 构造，不可相加，也不是 A/B。
- 尾轮固定而窗口增长时，基线的 `tool_projection` 随窗口线性增长：2,142 条 0.23ms、
  8,092 条 0.79ms、16,142 条 1.56ms；开查找栏的 `find_bar_query_update` 同样线性
  （0.66/1.28/2.05ms）。成本在 O(prefix) 的校验，不在尾轮投影。
  [scaling](round-8/layout-controls.json)
- 临时布局探针（已删除，输出记录在
  [provenance](round-8/mac-binary-provenance.json)）：Linux 上 `KimiMessage`
  size=73、stride=80；值相等的数组副本只在偏移 73..79（尾部 padding）不同，
  逐元素只比值占用的 73 字节时 8/8 全等。因此只在 `size == stride` 时整窗 `memcmp`，
  否则逐元素比较其值占用的字节。

## 产品修改

- 新增 `KimiMessage.sameWindow(_:_:)`（`Sources/WorkbenchCore/KimiProtocol.swift`）：
  1. 借用两侧连续存储按字节比较——位相同即值相同（副本保留同一批载荷指针）；
  2. 字节不同时用下标走 `==`，不经过迭代器，因而不拷贝元素；
  3. 存储不可借用时回落到原来的 `elementsEqual`。
  三条路径的答案与原 `elementsEqual` 一致，只是快慢不同。
- 三处"窗口未变"校验改用它：`ToolVisibilityProjection.canReuse`（每个 delta）、
  `projectTurns` 的 chunk 候选（翻页/新提示）、`ConversationSearch.hits` 的
  earlier 缓存（开着查找栏时每个 delta）。
- 校验通过时把存储的窗口换成刚比较过的这一份（adopt）：`reconcile(_:)` 会用重新
  解码的快照整体替换消息，值相等但载荷不同；采用最新副本让下一个 delta 回到按字节
  路径，否则该 prefix 余生都走慢路径。换入换出按值相等，复用条件不变。
  结构性副作用：投影不再额外固定一份过期窗口数组（未测 RSS，不主张内存收益）。
- `Sources/AgentWorkbench` 零差异；无新缓存、全局状态、异步/连接/权限或 UI 修改。

## 行为等价检查

新增 `checkWindowIdentityReuse`（`Tests/WorkbenchCoreTests/WindowIdentityTests.swift`）：

- 就地改早轮 tool_result 的 output（换成同字节长度的另一个词）、改 assistant 文本、
  改 `created_at`、加 metadata——四步都必须结束复用，且 rows/navigation/narrative/
  summary batch/payload cost 与一个全新模型（=完整重算）逐项相等；
- 同一份 wire 数据重新解码出的窗口必须继续复用（字节不同、值相同的那条路径）；
- 翻页与新 token 之后复用恢复；每步查找结果与全新 `ConversationSearch` 相等，
  并沿用上一步缓存的查询词，让"缓存没被失效"必然被抓到。
- 该检查在未改产品代码的两个对照构建上同样通过（91 PASS），不是为候选定制的。

已有覆盖保持不变：`checkConversationPresentationHistory`（24 步复用/交叉判定）与
`checkConversationPresentationPaging`（90 步随机翻页/语言/在线/live/running，
逐步与完整重算和 payload cost 对照）全绿。

## 伪影与不主张的变化

- **Linux edit-lines 的 fullLineDiff 场景 +23～+31%**（512 行 first/middle/last/insert/
  unchanged/trailing_empty/unicode 与 64 行同类）。证据表明不是算法退化：
  - 热点函数 `lineDiff`（4422 字节/1148 条指令）与 `fullLineDiff`（568/163）在基线、
    两个对照构建、候选四个二进制里逐条指令完全相同（地址归一化后 0 条差异）；
    `lines`（870/223、2337/583）与 `tally`（3142/785）四个二进制的大小与指令数也相同，
    只有 2/6/9 条重定位操作数不同，而两个对照构建的差异条数与候选完全一样。
  - 整进程 perf 计数器：指令数 -0.017%、cycles +1.05%、IPC 4.322→4.276；
    对照构建分别是 +0.46%/-0.31% cycles。做的功一样，执行变慢。
  - 两个对照构建（只加测试文件、只在 `Workspace.swift` 加一个未使用私有函数）
    在 512 行 first 上是 -0.4% 与 -1.2%；换五种 glibc 分配器 tunable 后候选的差距
    稳定在 +19～+31%，不是堆布局运气。
  - Mac 上同一批场景 +0.2～+0.3%（spread 3.65～5.37%），产品平台没有这个退化。
  结论：Linux 侧代码布局伪影，不采纳也不据此主张任何一方的收益。
  [对照、计数器与指令比较](round-8/layout-controls.json)
- **page_retained_cost**：Mac 0.655→0.770ms（+17.56%，spread 13.16%）、
  Linux 2.45→3.81ms（+55.5%）。同一台 Linux 上，没有任何产品改动的对照构建把这个
  指标移动过 -19.7%、-14.7%（一轮 3 次测量）与 +25.3%、-2.0%（另一轮），
  说明它对构建布局极不稳定。其工作量未变：90 步随机翻页检查逐步断言 payload cost
  与全新模型相等，而 reuseEnd/shift 由复用判定决定，`sameWindow` 的答案与
  `elementsEqual` 相同。翻页路径整体仍改善（Mac page_model_total -11.99%、
  older_page_full_chain -11.41%）。
- **retained_cost（每 delta）Mac -100%、Linux -96.4%**：两个对照构建是 +3.6%/+7%，
  所以确由本改动引起，但未逐项归因；方向与"投影改为固定最新窗口、少固定一份
  1.3MB 旧窗口数组"一致。作为观察记录，不作为主张的收益。
- **activity_init@320 Mac 0.007→0.008ms（+14.29%）**：该日志量化到 1µs，绝对差 1µs，
  六对全部同向；未归因，不作为退化结论。

## 结论

**采纳（以 Mac 为准）**：长窗口里每个流式 delta 的模型链 1.145→0.600ms（-47.60%），
其中 tool_projection 0.595→0.050ms（-91.60%）；开查找栏时 0.930→0.500ms（-46.24%）；
翻页整链 4.60→4.075ms（-11.41%）。窗口越长收益越大（校验原本是 O(prefix)），
但这是模型层同步工作，不乘成全应用 20x，也不主张 Linux 的 edit-lines 变化。

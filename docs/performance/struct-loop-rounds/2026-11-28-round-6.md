## 1. 这一轮要回答什么

round 4 把 ⑤（冷首搜 cf-match 调度）判为「缓议、不立项」，理由是**入口门槛未满足**：
历史 cf-match 79% 混合了 DataDetectors 文本准备与真实查询匹配、跨 harness 迁移、份额 ≠ 可转化量。
round 4 同时写明：**「下一步若继续 ⑤，只做 §6.5 第 1 项（同构分相归因），据其结果决定立项或永久缓议」**。

本轮就做这一项，判据是 §6.5 原文的三条：**分相对账闭合、不重复归属、足以计算保守净下界**。
门槛沿用 §6.4：按 16k 冷首搜墙钟，**2.5% ≈ 54ms**，且「2.5% 不是采纳门」。

round 4 还明确留下了缺口：当时日志里的 `rendered_calls=0` 记的是 `sameRenderedMessages`
**验证层**调用，**不是** `RenderedSourceCache.rendered()` 的 lookup/hit/miss/produce，
因此「冷首搜没有渲染缓存命中率、也没有文本准备时间」，**不能称文本准备已全覆盖**。本轮补这个缺口。

## 2. 方法与中立性

- **平台**：Mac mini M4，**release**（`swift build -c release --product WorkbenchChecks`）。
  Linux 侧只用于构建与单测通过性；**Linux 数字一律不用于裁决**——Linux Foundation 无 `NSDataDetector`，
  `ReplyDocument.linkMatches` 走 `bareURLRegex` 回退，**DD 这一层在 Linux 上根本不存在**。
- **规模**：`source_slots` = 2000 / 16000（与 round 3/4 同档；16k 档 `actual_messages = 18667`）。
- **查询**：`identifier`（literal，与 round 3/4 相同，故 `result_hits` 可逐值对照）。
- **三种缓存制度，各自独立进程**（`ConversationSearch()` 默认使用三个 `.shared` 缓存，
  同进程内第二次搜索必然已暖）：`cold-shared`（进程内首搜，= round 3/4 的 `find_cold` 口径）、
  `cold-fresh`（注入全新三缓存）、`warm`（先做一次不计时搜索再计时第二次）。
- **每次调用只跑 1 轮**（`SEARCH_PHASE_ROUNDS=1`），**每格重复 3 次独立进程**。
  原因已实测：同进程内第 2 轮起共享缓存已暖，`entries` 从 18667 掉到 3、墙钟从 2123ms 掉到 0.36ms，
  **不是重复的冷样本**。
- **两种语料**：`baseline`（与 round 3/4 **逐字相同**的夹具，用于与归档的 2155.871/2171.062ms 对照）
  与 `dollar-dense`（**额外**的敏感性对照臂，向 user / assistant 文本注入 `$…$` 与 `$` 价格）。
  **baseline 夹具未被修改**（红线：不改基准夹具制造收益）；dollar-dense **不替代** baseline，只用于给出下界。
- **矩阵**：sizes{2000,16000} × regimes{cold-shared, cold-fresh, warm} × corpora{baseline, dollar-dense}
  × 3 次重复 = 36，另加校准 sizes{2000,16000} × modes{(1,0),(0,0)} × 3 = 12，共 **48 个 cell**。

### 2.1 行为中性（三重证据，不是「应该没影响」）

1. **Mac release 全量套件（探针全开）**：`WorkbenchChecks` = **115 PASS / 0 FAIL / 0 SKIP、rc=0**
   （Linux 侧为 114 PASS / 0 FAIL / 1 SKIP，SKIP 是 Linux 无 AppKit 的 math 渲染烟测）。
2. **跨探针模式的产品答案不变**：`result_hits` 在三档模式 `(e0,t0)/(e1,t0)/(e1,t1)` 下**完全相同**
   （2k = **5001**、16k = **39999**）。`result_hits` 取自产品返回的 `ConversationFindResult`、
   **不经过探针**，正是为了「探针出 bug 也无法悄悄改变命中数」而这样设计。
3. **与历史归档逐值一致**：5001 / 39999 与 round 3/4 归档日志里的 `hits=5001` / `hits=39999` 相同；
   `cold-shared` 16k 墙钟 2123.205ms 与 round 4 的 2155.871 / 2171.062ms 同档（低 1.5%，属运行间抖动）。

### 2.2 探针自身开销（三档实测，**不假定可忽略**）

| size | `(e0,t0)` 近净 | `(e1,t0)` 仅计数 | `(e1,t1)` 全开 | 计数器开销 | 时钟开销 | 合计 |
| --- | --- | --- | --- | --- | --- | --- |
| 2000 | 272.283ms | 271.251ms | 269.707ms | −1.032ms | −1.544ms | −2.576ms（−0.95%） |
| 16000 | **2102.974ms** | 2130.704ms | 2123.205ms | +27.730ms | −7.499ms | **+20.231ms（+0.96%）** |

**这些是「本批观测差值」，不是探针开销的上界**（评审 run 1 **B4**，本人已独立复算确认）：
三档**非交替**、每档 3 次，取的是**中位数之差**——既没有交替设计对慢漂移的消除，也没有置信区间，
所以 **+20.231ms / +0.962% 只是这一批的观测差值**。16k 的时钟档差值本身为**负**（−7.499ms），
⇒ **同样不能据此认证任何「计时开销 ≤ X」的上界**。
2k 档三项差值均为负，只能说明**3 次重复的运行间抖动与该开销同量级**，
故 2k 档的时钟开销**不可分辨**，不得声称「时钟开销为负」。
⇒ **本轮不声明任何探针开销上界**；下文凡出现 0.96% 一律读作「本批观测差值」。
**由此，真实候选的「保守净下界」也未被建立**（见 §6 与 §7 对 §6.5 第 1 项第三条判据的更正）。
下文门槛一律按 **16k** 计，并额外给出以**近净墙钟 2102.974ms** 计的门槛作为对照。
（round 4 曾把份额写作「含探针开销口径」却未校准而被评审指出；本轮做了校准，
但**校准的产物只是观测差值，不是上界**。）

## 3. 分层口径（哪些可加、哪些绝不可加）

**顶层十一项互斥可加**，`wall = Σ(十一项) + unattributed`，`unattributed` **显式报告、不摊派**：

`timeline_make`、`reuse_instance`、`reuse_entrycache`、`l1_sources`（含 `role(of:)`）、
`l2_cache_lookup`（= `RenderedSourceCache.rendered` 的**查找前段 + 准入尾段**两段不重叠区间，`produce()` 除外）、
`l2_produce`、`l3_join`（含 `sameRenderedSources` 比较 + `sourceEnds` + `joined` 桥接）、
`l4_match`、`l5_excerpt`、`l5_store`、`assemble`（`next[entry.id]=…` 字典写入 + `hits += …` 数组追加）。

`assemble` **不在 §6.5 的五层里**，但 18,667 entries / 39,999 hits 规模下实测 **8.474ms**。
**下面三个数出自不同估计量，不得混写在一句里**（评审 run 2 指出本页原先又一次混用了）：
`median(assemble)/median(wall)` = **0.3991136%**；
`(median(unattributed) + median(assemble)) / median(wall)` = **1.2292266%**；
**逐次调整后残差百分比的中位** = **1.2402835%**（逐次 1.2403 / 1.1867 / 1.2415）。
**统一用「中位数之比」这一口径**：把 `assemble` 留在 `unattributed` 里，残差会从 **0.830113% 升到 1.2292266%**
（若改用逐次口径则是 0.8280% → 1.2402835%）——**两种口径都仍低于 2% 判据，结论不变**。
故**显式立层**的真实理由是：让残差留在「远小于预算」的量级，便于及时发现探针写错或区间重叠；
**不是**因为「它单独就能撑破 2% 对账预算」——该说法不受数据支持，已按评审 run 1 **N4** 撤回。

**嵌套项只报告、绝不相加**（round 5 的纪律）：

```
l2_produce ⊇ parse_normalize + probe_only_dollar_scan + parse_cmark_walk + render_walk
parse_cmark_walk ⊇ parse_link_split + parse_math_split      （parse_other = 导出残差）
parse_link_split ⊇ dd_matches
```

`probe_only_dollar_scan` 是**探针自有开销**（产品无此扫描），单列以免混入任何产品层。
`parse_other` 是**导出量**；若为负即代表区间重叠或探针写错，必须报告而不是当份额用（实测恒为正）。
`dd_matches` 的计时区间**包含** `contiguousUTF16(text)` 桥接——那是为 DD 付的成本，
排除它会低估 DD（round-16 已指出 bridge/DD 热叶的 97.6% 属 `linkMatches`）。
**Linux 分支故意不插桩**，两平台的 `dd_*` 数字永不合池。

## 5. 三个决定性结论

### 5.1 冷首搜 **90% 是文本准备，查询匹配只有 2.69%** ⇒ ⑤ 方向 A **未建立净下界，缓议**

方向 A 是「分块**并行匹配** + 确定性归并」，攻击的正是 `l4_match`。
**即使把 `l4_match` 降到 0**，收益上限也只有 **57.117ms**，而门槛是
2.5% × 2123.205 = **53.080ms**（按近净墙钟 2102.974ms 则为 52.574ms）。

**算术部分成立**：上限 − 门槛 = **4.037ms = 墙钟的 0.190%**；该 cell 三次重复的原始墙钟为
**2104.277 / 2123.205 / 2129.992ms**，**全距 25.715ms = 中位的 1.211%**；两者之比 **6.370×**。

**但本页此前据此写的「否证」不成立，已撤回**（评审 run 1 **B1**，且 PR #388 上
`chatgpt-codex-connector` 的自动评审提出**同旨独立意见**；本人已从 48 个原始日志独立复算）：

1. 该 cell 三次重复的 **`l4_match` 原值为 57.050 / 57.261 / 57.117ms，全距仅 0.211ms**，
   而整窗墙钟全距 25.715ms。**墙钟全距主要由其他层的波动贡献，不能用它来界定 `l4_match`
   这个上限的不确定性**——原推理正是这样做的，故**「余量比全距小 6.4 倍 ⇒ 无法区分」这一步作废**。
2. n=3 的全距**既不是计时误差界、也不是置信区间**；「无法区分」只支持**精度不足**，不支持「不可达」。
3. 「任何非零并行成本都会把净值压到门槛以下」在算术上**错误**：实测余量为 **+4.037ms**，
   并行新增成本**小于** 4.037ms 时净值仍在门槛之上。§6.5 第 4 项列出的那些成本
   （worker 输入/ranges/结果副本的并发峰值、块冻结与排队、归并与入账、任务析构尾巴、
   取消后仍占用的 CPU 与内存留存、重试与旧请求竞争）**本轮一项都没有测**，
   故**不能断言其总和必然超过 4.037ms**。
4. 「若要推翻须证明 `l4_match` 被低估、而不是证明并行开销更小」同样**撤回**：
   证明新增开销足够小**正是**建立净下界的正常路径。

**判定（降级）：方向 A 未建立 >2.5% 的保守净下界 ⇒ 缓议，不立项。**
这是**精度不足**，**不是**「已证明不可达」。按评审要求，本降级**不要求重跑 Mac**——
更多墙钟重复本身仍不足以支持「否证」。若日后要恢复更强措辞，须先给出
**对 `l4_match` 单独做交替重复得到的净收益上界及其不确定性**，
**以及并行新增成本的实测依据**，两者缺一不可。

### 5.2 DataDetectors 单项 = 墙钟的 **65%**；「成本由调用次数主导」**降级为待检验假说**

`dd_calls = 178,665` 次 / 16,001 个 source ⇒ **平均每 source 11.1658646 次**（通常舍入 **11.17**；
因为 `linkBareURLs` 按 **inline run** 调用 `linkMatches`，不是按 source）；
`dd_utf16 = 3,912,513` ⇒ **平均每次调用只处理 21.8985979 个 UTF-16 字符**（**21.9**）；
`1381.978ms / 178,665 = 7.73502365µs`（**7.74µs/次**）。
〔评审 run 1 **N4**：本页原写 11.16 / 7.73 是**截断**而非舍入，已改为通常舍入值；精确值一并保留。〕

⇒ 本页此前据此断言「**每次调用的固定开销主导，不是数据量主导**」。
**该机制归因超出证据，降级为待检验假说**（评审 run 1 **B5**，已复算确认）：
平均输入长度短、每调用均摊时间高，**都不能区分**「固定开销主导」与
「成本随长度走、只是这里的长度恰好很小」。本轮**没有独立控制调用数与文本长度**。
反向证据：dollar-dense 的**按字节分类组平均 2.512µs/调用**（33.497ms / 13,336）、
**其余组约 8.230µs/调用**（(1503.893−33.497)ms / 178,662）——
**每调用成本本身随文本变化**，因此同样**不得**把「DD 成本与文本长度成正比」写成已确定事实。
两种说法目前**都只是假说**；要判定需做**长度分箱**或「固定长度、变调用数」的对照实验。

**份额的独立性声明同样收窄**：两臂的 `dd/wall` 分别为 65.09% 与 65.05%，
只支持「**在这两个高度同源的对照臂中份额接近**」，
**不支持** DD「与语料无关」或「不依赖 `$` 密度」这类全称结论。
（份额量级本身另有一处旁证：在**本循环自己的 harness 里独立复现**了
`RenderedSourceCache` / `ReplyDocument` 注释中 round-16 的 **66.6%**；
历史值按 §6.4 不得直接迁移，故这是**复现**而非引用。）

### 5.3 `parse_other` = **18.41%**（**两臂接近**；不外推为「与语料无关」）

cmark 解析 + `inlines`（Markup → `ReplyInline`）转换 + block 分派 = **390.841ms**
（逐次导出残差的中位；dollar-dense 428.720ms），是**第二大单项**、门槛的 **7.4 倍**，且**不依赖 DD**。
〔评审 run 1 **B5**：本页原写「同样与语料无关」「不依赖 `$` 密度」。两臂份额接近只支持
「**这两个对照臂中接近**」，故已**收窄为两臂观测**，不作全称结论；`$` 密度对 `parse_other`
的影响本轮**未做受控实验**。〕

## 6. 「跳过 DD」候选的两夹具归因净值代理 —— 以及为什么它**不能**立项

代码走查**曾**提出一条候选等价条件。**它已被推翻**（见下方 B2 更正），
下面保留原推理链只为说明**它错在哪一步**——**本节不主张任何成立的安全跳过条件**：

> `linkBareURLs` 无条件调用 `linkMatches`（**不看 `documentLinks` 标志**）；
> 其切分本身对 `renderedText` 的 `runs.map(\.text).joined()` 是**拼接不变量**（prefix+link+suffix 拼回原文）。
> **但** `ReplyMath.splitInline` 在 `linkBareURLs` **之后**执行，其 guard 含 `run.link == nil`
> （`ReplyMath.swift:282`），而 `ReplyMath.split` 会把 math 段的 `.text` **替换为 `\u{FFFC}`**
> （`:308-310`）⇒ **`runs.map(\.text).joined()` 对 math 切分不是不变量**，
> 于是 **DD 的结果确实会改变搜索用的渲染字节**。
> ⇒「搜索路径白付 DD」这一直觉**被否证**，任何跳过 DD 的做法都必须带前置条件。
>
> **原先声称的「可跳过条件（已证）」已被推翻，撤回**（评审 run 1 **B2**；
> 本人已在 Linux debug 上**独立跑出反例**，日志见证据目录 `b2-entity-decoding-verification.log`）：
> 原论证是「source 经 `ReplyMath.normalizeDelimiters` 后**不含 `$`（字节 36）**
> ⇒ `splitInline` 的 guard 对每个 run 都恒等 ⇒ `linkBareURLs` 的切分不可能影响渲染文本」。
> **缺口在于 `normalizeDelimiters` 之后还要经过 cmark**：锁定的 swift-cmark 0.8.0 **会解码字符引用**
> （`houdini_html_u.c:53-91`、`inlines.c:864-877`），`&#36;` / `&#x24;` 都会产生 `$`，
> 再由 `ReplyDocument.swift:220` 把解码后的 `Markdown.Text.string` 交给后续处理。
> ⇒ **「规范化源无字节 36」并不保证「解析后的 run 无 `$`」，充分条件不成立。**
>
> **实测反例（两条，均由产品代码直接执行得到）**：
> - `见&#36;见https://example.com/a y&#36;尾`：输入**无**字节 36，解析后 run 为
>   `见$见` / 链接 run / ` y$尾`——正是本仓已钉死的 **spanning 形状**
>   （`LinkScanMaterializeTests.swift:96`）：有链接切分时美元符保持字面文本；
>   若去掉该切分，完整美元符对就能被 math 切分，拼接文本将变为 `见\u{FFFC}尾`。
> - `&#x24;x&#x24; https://e.com/a`：输入**无**字节 36，解析后**首个 run 已是 `\u{FFFC}` 且
>   `math: "x"`**，即 math 切分**确实发生**、渲染文本已被改写。
>
> **因此**：`dd_calls_skippable` / `dd_ms_skippable` 这些原始日志**保留**，但其解释必须收窄为
> **「按规范化源的字节 36 分类的成本」**——它是一个**成本分类口径**，
> **不是**通用的语义安全证明，**不得**当作「可安全跳过 DD 的集合」。
> 本轮**未运行任何新的 Mac 实验**来得到上述反例（它由锁定依赖与产品源码推导 + Linux 行为验证）。
>
> 另两条仍然成立、与 B2 无关：检查必须针对**规范化之后**的文本
> （`normalizeDelimiters` 会把 `\(...\)`/`\[...\]` 变成 `$...$`）；
> 且任何扫描本身不免费（`ReplyMath.swift:275-281` 记录 round-17 的 `contains(36)` guard 占 5.48%），
> 故若要保留某种字节扫描，必须是**每 source 一次**的 memchr 级。

实测**按该字节分类口径**的成本分布。
〔评审 run 1 **B4**、run 2 更正措辞：下表**「归因净值代理」那一列**（**不是**最后两列——
最后两列是**门槛**与**判定**）**不是实际候选的净收益**，而是**由分项中位数组成的归因净值代理**
（`1366.868` 与 `18.452ms` 的减法本身正确，逐次差的中位分别为 **1366.926 / 18.463ms**）；
方案的**完整新增成本**与**可用的探针开销界**都未建立，故**真实保守净下界未被建立**。
两臂取最差也**不是**所有合规产品语料的下界——它只是这两个夹具的下界。〕

| 语料 | 无 `$` 的 source | 按字节分类的 DD 调用 | **分类到的 DD 时间** | 减去 `$` 扫描成本 | **归因净值代理** | 门槛 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| baseline（**不含任何 `$`**） | 16001/16001 = **100%** | 178,665/178,665 = **100%** | **1381.978ms** | −15.110ms | **1366.868ms** | 53.080ms | 超门槛 **25.75×** |
| dollar-dense（83% source 含 `$`） | 2668/16001 = **16.67%** | 13,336/191,998 = **6.95%** | **33.497ms** | −15.045ms | **18.452ms** | 57.798ms | **低于门槛（0.32×）** |

**关键观察**：dollar-dense 下「按字节分类的**调用**占 6.95%」而「分类到的**时间**只占 DD 的 **2.23%**」
（精确值：2668/16001 = 16.67396%；13336/191998 = 6.94591%；33.497ms = DD 的 2.22735%）——
因为不含 `$` 的是**短的 tool 源**、含 `$` 的是**长的散文源**，
而 §5.2 已复算出这两组的每调用成本为 **2.512µs vs 8.230µs**。
⇒ **分类到的时间对语料的敏感度远高于调用数，用调用数外推会严重高估。**
（「DD 成本与文本长度**成正比**」仍只是假说，见 §5.2；此处只用到「两组每调用成本相差 3.3 倍」这一实测事实。）

**结论：该候选的净值取决于真实会话语料的 `$` 密度，两夹具的归因净值代理区间为
18.5ms ～ 1366.9ms，横跨门槛两侧；而真实保守净下界未被建立（B4）。**
更重要的是，**B2 已推翻该分类的语义安全性**——即使收益足够，这个口径也**不能**直接当作可跳过集合。
而按本循环红线，**本任务无权触碰用户真实数据**，故真实 `$` 密度**不可测**
⇒ **入口门槛「保守净下界严格 > 2.5%」未被建立** ⇒ 按 §6.4「不足即缓议」与 §10「不降低测量标准硬做」：
**缓议，不采纳、不实现。**

**必须写在明处的一条**：baseline 夹具**恰好一个 `$` 都没有**（`ReplyMath.swift:277-280` 的注释也这么说）。
若只报 baseline，结论会是「超门槛 25.75 倍」——**那是夹具的偶然性质**，
**不能外推为真实语料的产品收益**。这正是本轮额外造 dollar-dense 对照臂的原因。
〔评审 run 1 **N5**：本页原写「据此立项就等于用夹具制造收益（红线）」。该定性**过强、已收窄**——
**未修改的既定固定场景**可以提供合法的**该场景**候选依据（本循环 round 1/2 的采纳正是如此），
红线禁止的是**修改夹具或语义来制造收益**，不是「引用未改动的夹具」。
**保留的限制是「不外推为真实语料收益」**；本轮判缓议是**额外的保守选择**（因为真实 `$` 密度无权测、
且 B2 已推翻安全性），**不是红线的必然要求**。〕

## 7. 裁决

- **⑤ §6.5 第 1 项（同构分相归因）：前两条判据满足，第三条未建立。**
  **满足**：§4 的对账闭合（**24 个计时 cold run** 逐 run 满足原 2% 相对预算、不用 floor；
  未归属**逐次百分比中位** 0.8280%。**warm 的 12 个 run 不在此列**，其相对残差 10.83%–18.25% 全部超 2%，
  只靠 1ms 绝对下限通过，故**不声称 warm 的相对对账闭合**）、
  §3 的不重复归属（十一项互斥可加、嵌套项只报告不相加、逐 run 嵌套不变量全过）。
  **未建立**：第三条「足以算**保守净下界**」——评审 run 1 **B4** 指出（本人已复算确认）
  §2.2 的三档差值只是**非交替的观测差值、不是探针开销上界**，§6 的 `1366.868 / 18.452ms`
  只是**分项中位数组合出的归因净值代理、不是实际候选净收益**，方案的完整新增成本也未测。
  ⇒ **本页此前写「三条判据全部满足」，撤回。**本轮的**归因本身**是成立的（这是它的主要产物），
  但它**不能**被引用为「已给出保守净下界」。
- **⑤ 方向 A（分块并行匹配）：未建立 >2.5% 的保守净下界 ⇒ 缓议**（§5.1，攻击 2.69% 的层，
  余量 +4.037ms）。**原写「否证」已撤回**（评审 run 1 B1 + PR 上自动评审同旨意见）：
  `l4_match` 自身三次原值全距仅 **0.211ms**，用整窗墙钟全距 25.715ms 界定它的不确定性无效；
  且并行新增成本**一项都没测**，不能断言其必然超过 4.037ms。
- **⑤ 方向 B（时机前移 / 预热 rendered source）：仍缓议。** 它攻击的 `l2_produce` 有 1908ms，量级足够，
  但本质是**成本搬迁而非消除**——预热仍要付同样的 DD + cmark 成本，只是移到挂载/空闲期。
  §6.5 第 4 项要求的 B 侧账（挂载/空闲预热成本、首次搜索净变化、**无搜索发生时的纯浪费**、
  失效重做、驱逐其他窗口缓存的代价）**本轮未测** ⇒ 不能立项。
- **⑤ 方向 C（按视口收缩范围）：维持 round 4 的否决**（违反红线 3 与查找契约 2）。
- ⇒ **⑤ 整体：永久缓议**（A **未建立净下界** / B 成本搬迁且未量化 / C 否决），
  符合 round 4 §6.7 的处置约定。**注意「永久缓议」的依据是三个方向都不满足入口前置，
  不是「A 已被证明不可达」**——若日后拿到 `l4_match` 的交替重复上界**与**并行新增成本实测，
  A 可以重新申请入口，无需推翻本轮任何测量。
- **新开队列项 ⑧ =「冷首搜的文本准备成本（`l2_produce` = 墙钟 90%）」，状态：待证明候选**，两个子方向：
  - **⑧(a) DataDetectors 调用粒度**：**65% of wall**（两臂 65.09% / 65.05%，**只声明两臂接近**）、
    **7.74µs/次、21.9 字符/次**。〔评审 run 1 B5：原写「与语料无关」「成本由调用次数主导」，
    前者收窄为两臂观测，后者**降级为待检验假说**——见 §5.2 的 2.512µs vs 8.230µs 反向证据。〕
    若能把 DD 调用数降低一个量级，收益量级为数百毫秒至 1.38 秒（**这是量级估计，不是净下界**）。
    **⑧(a) 之外另有一条不需要产品决策的路径**：`linkMatches(in:)` 是 `text` 的**纯函数**
    （`linkDetector` 是进程级 `static let`），故对输出做**按 UTF-8 字节精确键的记忆化**是语义等价的，
    沿用的正是 `RenderedSourceCache` 已在产的同一套纯度假设（含 locale generation 失效）；
    它减少的正是调用次数。**但不得声称其「纯赚或中性」**（评审 run 2 指出这是**无据的不回归保证**）：
    语义等价只说明**输出不变**，**不说明成本不增**——字节键的复制与哈希、未命中、加锁、
    准入/驱逐与常驻内存**都会新增成本**；而且 `RenderedSourceCache.swift:26-36` 的注释本身就
    **区分了「检测器只构造一次」与「匹配时结果稳定」这两种不同性质的假设**，
    后者是**假定的**、不是已证的。故它只能记为**「在明示假设下待证明的候选」，
    净成本与内存账均未结**。该路径已作为 round 7 的**归因**对象，
    **本轮不对其收益作任何声明**。
    **入口前置**：改变 DD 调用粒度会改变**链接检测结果** ⇒ 影响 UI 渲染，
    并经由 `splitInline` 的 `run.link` guard 影响**搜索文本** ⇒ **属语义变更**，
    须**产品决策 + 字节级 oracle**（对全部 hit 字段与渲染文本逐字节比对），**不得单方面实施**。
  - **⑧(b) 搜索路径绕开 cmark/`inlines` 树**：`parse_other` = **390.841ms（18.41%）**
    （逐次残差的中位；两臂接近，**不外推为与语料无关**）。
    搜索只需要纯文本，理论上可绕开完整 block/inline 树。
    **入口前置**：必须与 `renderedText(ReplyDocument.parse(source))` **逐字节相同**
    （含表格、列表、引用、代码围栏、math 的 `\u{FFFC}` 规则），否则改变搜索结果；
    这等价于重写一遍 cmark 遍历，**风险高，须先有字节级 oracle 才谈实现**。
- **⑦(a) 缓议**：`id.getter` 六窗 inclusive 中位 **6.5ms**（逐窗 12/5/6/5/8/7），
  每行 3 次 → 1 次最多省 2/3 ⇒ **CPU 上限 4.333ms** < 门槛 **4.387ms**（2.5% × 175.475ms）；
  即使按 profiler 窗口中位 168.775ms（门槛 4.219ms）也只超 0.114ms，
  而 round 5 实测噪声带换算为 **3.836734 / 8.672822 / 10.236010 / 15.616169ms**
  （通常舍入 **3.84 / 8.67 / 10.24 / 15.62ms**；本页原写 10.23 是截断，已按评审 run 1 N4 更正），
  该余量比最窄噪声带小约 **33.7 倍**（粗略量级描述，**不是误差界**）；
  且该上限还需同时成立三个乐观假设（全部 `id.getter` 时间来自 `contents`、耗时严格正比于调用次数、
  CPU 节省 1:1 转为窗口缩短——而 round 5 实测主线程仅 **63.456445%** on-CPU）。
  ⇒ 按 §10「净下界不足 → 缓议，不降低测量标准硬做」，**不跑 Mac A/B**。
  **⑦ 整体仍为「待证明候选」**：其 10ms ≈ 5.9% 的上界来自 `body` 全部自有工作，
  惰性/分页 `contents` 那条路径未被本算式否证（但须先满足 `shardB-A2-design.md` §11.4，
  且 `entry.id` 是锚点/折叠/阅读位置的键，动它碰语义红线）。
  另：本轮实测**搜索路径**的 `id_getter_calls = 114,667`（18,667 entries ⇒ 每 entry 6.14 次），
  但 `reuse_instance + reuse_entrycache` 合计仅 10.1ms、且 `id` 求值分散在多层，
  **本轮未单独隔离 `id` 在搜索路径的成本**，故**不据此对搜索路径的 id 优化下任何结论**。
- **停止规则计数仍为 0**（归因/裁决轮，按 §10 不计入）。

## 8. 过程缺陷与自我更正（全部就地留痕）

1. **两次派发被自己的守卫误拒**（`struct-6-search-phase-20261128` 与 `…b`，均 `exit=1`、**未产出任何测量**）。
   根因：新加的「二进制新鲜度」守卫按 **mtime** 判定，而 **SwiftPM 的 up-to-date 检查基于内容**——
   重新 apply 补丁得到**逐字节相同**的源文件时它**合法地跳过重链**，二进制 mtime 与 sha 均与试跑时相同。
   job b 的日志显示**三个内容标记全部命中**、二进制 sha 与刚试跑成功的那次**完全相同**，
   ⇒ **是守卫错了，不是构建错了**。
   修法：把**版本字符串写进补丁**（`SearchPhaseProbe.probeVersion = "search-phase-probe-v3"`，

# 性能与体验优先的技术选择

框架是手段。优先减少用户输入、切换和阅读时的实际工作量，并保持草稿、阅读位置、
审批与重连状态正确。每次技术迁移先定位问题，保留对照场景，再验证结果。

## 当前决定

采用 Observation，并把原生会话的输入区与阅读区分离。基线的 40 次草稿修改触发
40 次阅读区 body 重算；迁移后为 0 次。输入框更新及流式快照刷新均有正向检查。
这证明去掉了无关重算，不代表已经测得输入延迟、CPU 或 FPS 改善。

## 候选技术与引入条件

| 技术 | 适合解决的问题 | 引入或推广前的证据 |
| --- | --- | --- |
| Observation + 小型状态对象 | 草稿、目录、快照之间的无关刷新 | 真实挂载视图的失效计数，正向刷新检查，功能回归 |
| Swift Concurrency、actor / 后台纯计算 | 主线程上昂贵的解析、搜索、投影，以及乱序结果 | Instruments 中的主线程占用；取消、旧结果、数据复制开销检查 |
| TCA | 多步流程、子功能组合、依赖替换和异步副作用的测试 | 在远端设置或归组等有边界的功能中对比；测试覆盖更好，输入/切换响应与内存不退步，再考虑推广 |
| AppKit 列表复用 | 高密度列表的布局、行复用和滚动成本 | 先分析现有 AppKit transcript 与 SwiftUI 目录的瓶颈，再选择性替换；保留焦点、选择、可访问性与阅读锚点 |
| SwiftData / 数据索引 | 本地查询、持久化与数据关系的成本 | 实际存储或查询瓶颈，迁移/损坏恢复设计，主线程与磁盘开销对照 |

TCA 的状态、Action、Reducer、Effect、依赖与测试机制适合流程组合；它也使用
Observation。当前已定位的问题是视图读了过多状态，因此先修复依赖边界。
是否引入 TCA 将由独立功能试验决定，不把更换框架作为性能结论。

## 后续验收顺序

1. 按原生会话的边界迁移 Kimi，但保留其流式更新、分页、子任务及待发送恢复语义。
2. 分别测量输入/IME、切换到可读内容、历史加载后锚点、持续流式输出和内存增长。
   使用同样数据、窗口、工具链，多次运行；把功能检查与时间测量分开。
3. 在 Instruments 中找出耗时 body、布局与主线程阻塞；只针对证实的热点选择缓存、
   后台计算、增量投影或控件替换。缓存必须有明确的失效与内存上限。
4. 对复杂流程试验 TCA。保留原实现的验收场景，比较取消/重试/恢复的正确性、
   主线程占用、内存及构建成本，再决定扩大范围。

离线 fixture 不证明真实 SSH 恢复、模型质量或长时间真实使用的流畅度；这些需要
独立的真实会话验收。最终目标始终是用户能持续输入、稳定阅读并可靠地恢复工作。

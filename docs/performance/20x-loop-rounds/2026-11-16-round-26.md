## 设计前提（双平台穷举探针）

**规范桥扫描**（round-22 操作性机制：String 规范 `==`，全 1,112,064
标量；Linux swiftc -O 编译 + macOS 解释器模式）：与 "："（U+FF1A）、
":"（U+003A）、" "（U+0020）规范相等的非自身标量 = **双平台均 0** ⇒
字节搜索**规范完备**（不存在藏在不同字节后的分隔符出现）。多标量
序列不能合成原子（规范分解逐标量作用；组合符不能湮灭成 ":"/" "
——round-22 多标量组合论证同型）。脚本+双端输出归档
[round-26/probe/](round-26/probe/)。

## 改动（v1=77157a9；产品 2 文件 + 钉死 1 新文件）

`NarrativeDelimiterScan.firstOccurrence`：单遍字节扫描找 pattern
（EF BC 9A / 3A 20）首次出现；命中后**双侧边界证明**：
- 前侧（GB9b）：仅 Prepend 标量可向前吸收分隔符；一切 Prepend 均
  非 ASCII ⇒ 前邻字节 ASCII 或串首即证明安全；非 ASCII 前邻解码后
  查 `String.isPrependScalar`（既有钉死集）。
- 后侧：任何向后结合标量（Extend/ZWJ/Mn/Mc/Me + round-24 钉死融合
  七标量）会把分隔符末字符吸入后续簇 ⇒ 查 `String.beginsBindingMark`
  ——**其完备性由 round-24 fusionGap==0 穷举走查钉死，本轮跨调用点
  复用同一谓词**（两谓词由 private 改模块内可见；无公开 API 变化）。
- 不可判定 ⇒ `.inconclusive` ⇒ 调用方回落**原 `range(of:)`**——legacy
  语义在证明不及处逐位裁决；无字节出现 ⇒ `.absent`（由规范桥零扫描
  保证 range(of:) 同样找不到）。
- 首现同一性：按序检查字节出现，首个确认出现必为首个 grapheme 匹配；
  首个不可判定出现即整体交回 range(of:)。

`narrativeText` 仅替换分隔符搜索步骤；clean/缓存/条件/优先级顺序零
改动；分隔符字面量与字节 pattern 由钉死断言保持同步。

等价论证四层：① UTF-8 自同步（pattern 字节只能落在标量边界）⇒ 无
假位置；② 双侧边界证明 ⇒ 无假阳性；③ 规范桥零 + 多标量不可合成 ⇒
无假阴性；④ 不可判定回落 ⇒ GB9b/融合角落的平台分歧逐位保留
（round-17 探针记录）。

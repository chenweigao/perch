## 改动（faafa83 → 混合守卫 3aad9b7 → 前边界修复 66a94d5；单文件 `ReplyMath.swift`）

入口守卫 `utf8.contains(92) && (contains("\(") || contains("\["))` →
`utf8.contains(92) && hasDelimiterStart(source)`。`hasDelimiterStart` 单遍
UTF-8 字节扫描：

- **等价论证**（钉死死锁）：ASCII 双字节模式的字节邻接是 Character 序列
  匹配的**必要条件**（UTF-8 自同步：ASCII 字节不出现在多字节序列内部）；
  找到的字节对在后继字节为 ASCII 或 EOF 时 **grapheme 精确**——反斜杠恒为
  独立 Character（ASCII；CR 只与 LF 配对），而一切能延长括号字形的标量
  （Extend/SpacingMark/ZWJ）均非 ASCII；后继非 ASCII ⇒ 字节级不可判定 ⇒
  **回落原 grapheme 搜索**（仅含分隔符字节对的源到达，常见无对源零回落）。
- **保留 contains(92) 前置快速拒绝**（v2，3aad9b7）：无反斜杠源经标准库
  快速搜索即刻拒绝，字节对扫描只在含反斜杠源上运行——v1 无条件标量扫描
  在 Linux 温路径/活动路径留下的 +1 打印格～+5% 位移信号由 v2 消除
  （见迭代节；复核发现 6 提醒：该三路径不调用本函数，翻转支持构建级
  相关而非标量扫描成本的直接证明）。
- **双侧边界证明**（v3，66a94d5，复核 BLOCKING 发现 1 修复）：字节对
  快速接受必须同时证明**前边界**——反斜杠前字节为 ASCII 或位于串首。
  反例：U+0600（GCB=Prepend）按 GB9b 与后随反斜杠**前向融合**为单一
  Character，旧 contains 不中、源必须保持字面，而初版快速路径误纳转换
  （该危险 ConversationProjection.swift:25 早有登记）。一切 Prepend 标量
  均非 ASCII、唯一 ASCII-ASCII 融合 CR×LF 不吞反斜杠，故 ASCII/串首前驱
  即字节级证明；非 ASCII 前驱 ⇒ 不确定 ⇒ 回落各平台自有 contains——
  **逐位复现每平台旧行为**（含实测发现的 Linux corelibs 分歧，见钉死节）。
- **旧守卫/扫描不对称角落逐位复现**：括号被组合符延长时 `contains("\(")`
  看不见（守卫拒绝），但只要有另一处精确对开门，字节级 Boundaries 扫描
  照样转换延长对——该不对称是现状行为，钉死显式收录（单独延长对保持
  字面 vs 混合时双双转换）。

`Sources/AgentWorkbench` 零差异；Linux 与 Darwin 走同一新代码（无平台
守卫——本轮改动平台中立）。

# 大会话展示投影成本测量（2026-10-09）

## 问题

首次切到未被缓存的大会话时，`ConversationPresentationModel.update` 在主线程
同步做全量投影。是否值得引入后台预计算（选中即算、挂载即命中）取决于这一步
的真实成本——先测量，再决定。

## 方法

`WorkbenchChecks` 增加 `WORKBENCH_BENCH=1` 门控的 `benchPresentationUpdate`：
混合散文/工具调用/工具结果/代码块消息，100–2000 条（约 43KB–868KB 正文），
release 构建，每个规模 5 次取中位数，整机 3 轮。冷读 = 全新 model 的首次全量
投影；追加 = 同一 model 上流入一条新助手消息（逐轮 memo 命中）。

## 结果

| 消息数 | 冷读中位数 | 冷读最大 | 追加中位数 |
| --- | --- | --- | --- |
| 100 | 1.8ms | 5.1ms | 0.3ms |
| 500 | 8.9ms | 9.6ms | 1.3ms |
| 1000（缓存准入上限） | 17.8ms | 18.6ms | 1.4ms |
| 2000（超出准入，不缓存） | 35.2ms | 36.8ms | 3.3ms |

逐轮 memo 化让流式追加稳定在 1–3ms；冷读与消息数近似线性（约 18µs/条）。

## 结论：不做后台预计算

- 可缓存范围内（≤1000 条）首次打开最多约 18ms，且每个会话每次启动只付一次
  （LRU 8 个）；切换验收的整链路中位数约 60ms，投影占比约 10%，不是切换
  卡顿的主要成分。
- 后台预计算需要把非 Sendable 的可变 model 跨 actor 交接、处理输入漂移与
  缓存竞争；按项目既有证据门槛（`performance-and-technology.md`：后台化需要
  单独的 profiling 与取消/身份/外观证据），这个收益规模不值得引入该复杂度。
- 真正会反复付全量成本的是 >1000 条消息的会话（永不进共享缓存）。若真实使用
  中这类会话的切换卡顿可感知，下一步选项是按预算上调准入上限（内存换时间，
  需 RSS 对照），而不是后台化。

## 复现

```sh
swift build -c release --target WorkbenchChecks
WORKBENCH_BENCH=1 .build/release/WorkbenchChecks
```

门控默认关闭，不影响既有检查（47 项 PASS）。

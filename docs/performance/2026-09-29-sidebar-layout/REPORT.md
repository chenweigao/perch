# 目录内容、分区与行高的独立诊断

**下一步优先试验分区重排时的稳定行身份，其次处理状态变化引起的行高波动。**
三轮固定二进制实验中，只改文字或顺序约 10–11ms；置顶分区与成员变化约 29.5ms。
对完全相同的状态变化保留 48pt 行高，可将 21.5ms 降到 17.5ms，约改善 19%。
正文没有重新协调或测量。这给出了具体的目录渲染调查方向，不构成换 TCA、SwiftData
或全面替换列表控件的理由。

本轮新增诊断场景和真实行几何验收。固定高度仅由验收模式启用，正式界面的
34/48pt 行高策略保持原样；没有发布一个所有行都占两行空间的产品改动。

## 六种刺激，同一诊断构建

Apple M4、16 GiB、macOS 27、Swift 6.4、release -O，窗口 1280×820。
数据统一为 500 条在线、未归档记录，清空任务组和初始置顶；最近列表最多 20 条。
选中会话与草稿始终固定。每次先验证初始布局并等待 200ms，再执行 80 步。

| 场景 | 实际变化 | 三轮中位数的中位数 | 循环 CPU 中位数 |
| --- | --- | ---: | ---: |
| 无变化控制 | 重放相同目录，没有工作区写入 | 2.20ms | 0.034s |
| 内容 | 更新可见 20 行标题，顺序和高度不变 | 10.50ms | 0.887s |
| 顺序 | 循环移动相同 20 行，内容与高度不变 | 10.21ms | 0.818s |
| 置顶分区 | 交替置顶/取消前四条，分区与可见成员变化 | 29.47ms | 2.203s |
| 状态与动态行高 | 前 20 行在待处理/待回看间切换，34↔48pt | 21.52ms | 1.587s |
| 同样状态、固定行高 | 相同数据与文字显示变化，始终保留 48pt | 17.47ms | 1.242s |

各轮中位数范围：内容 10.41–10.90ms，顺序 9.70–10.73ms，置顶 27.95–29.69ms，
动态行高 21.34–21.56ms，固定行高 17.06–18.38ms。固定高度对照的循环 CPU 约
减少 22%，但它保留了原本单行记录不需要的垂直空间，改变了可见区域的内容密度。
因此不能把它理解为无代价、已可推广的整体性能优化。

置顶时原有 20 条最近会话仍保留额度，加上四条置顶，总行数变为 24；取消后回到
20。这个场景同时包含分区出现/消失、跨分区移动和可见成员增删，**尚未把三者再
分开**。不能用 29.47−10.21ms 声称这是分区标题的独占成本，六种耗时也不能相加。
它们是同一程序的不同工作量，不是新旧版本 A/B；规范化数据也与此前混合压力
场景不同，不能直接比较绝对毫秒数来声称版本退步或改善。

## 用实际行几何确认场景

所有场景使用同样的挂载行探针。每步确认会话数据、选中/置顶状态、从上到下的
物理顺序，以及实际 34/48pt 高度；确认之后结束延迟计时。不是仅等待模型字段更新。

| 每轮 80 步累计 | 高度变化 | 行顶边移动 | 可见集合加入 / 移除 | 行 body 重算 |
| --- | ---: | ---: | ---: | ---: |
| 无变化 | 0 | 0 | 0 / 0 | 0 |
| 内容 | 0 | 0 | 0 / 0 | 1600 |
| 顺序 | 0 | 1600 | 0 / 0 | 1596–1598 |
| 置顶分区 | 0 | 1600 | 160 / 160 | 2240 |
| 动态行高 | 1600 | 1520 | 0 / 0 | 1600 |
| 固定行高 | 0 | 0 | 0 / 0 | 1600 |

动态/固定高度对照的 body 次数相同，但耗时不同；上一轮“减少 body 次数却没有
提速”与本轮结果共同说明，要区分视图计算、结构更新和布局。加入/移除是按会话 ID
统计的可见集合变化，**不是视图创建/销毁计数**，尚不能证明跨分区究竟复用了多少
原生或 SwiftUI 子树。

非空刺激每轮侧栏根 body 为 80 次；无变化控制为 0 次。所有场景的正文 configure、
内容协调、行创建/测量阶段均为 0 次。结束时额外确认选中正文和草稿保持正确。

## 独立 CPU 采样

计时完成后，分别对置顶、动态高度和固定高度另做一次 Time Profiler 采样，以
`SidebarLayout` signpost 的半开区间排除启动、等待和后续滚动。时间样本不混入
这些采样运行；每个 time-profile 导出只有一个表和目标应用的一条主线程。

| 互斥的主线程采样上下文 | 置顶分区 | 动态高度 | 固定高度 |
| --- | ---: | ---: | ---: |
| 侧栏应用栈 | 160ms | 118ms | 111ms |
| 剩余 AttributeGraph 更新栈 | 958ms | 744ms | 612ms |
| 剩余 AppKit 布局栈 | 592ms | 482ms | 396ms |
| 其他 | 383ms | 240ms | 102ms |
| **合计** | **2093ms** | **1584ms** | **1221ms** |

置顶场景约 74% 的主线程采样落在框架图更新/布局上下文。这是采样上下文，不是某个
控件的独占成本；延后执行的框架工作通常不带原始功能调用者，不能把 160ms 当成
侧栏总成本。普通 inclusive 栈权重相互重叠，不能相加。这些数字也不是墙钟占比或 FPS。

固定高度第一次采样在应用行为检查通过后，Instruments 保存超时。该记录作为失败
保留，没有用于采样统计；相同二进制的新目录重试成功，上表使用重试结果。

## 架构方向

1. **先试验统一行身份的分区投影。** 当前置顶、最近会话位于不同 ForEach/分区路径。
   小范围比较同一稳定列表中的带 ID 行与分区标记，先补真实行宿主身份/创建次数，
   再测置顶和联合更新。源码提供了这个调查入口，但本轮没有证明迁移父路径就是
   29ms 的唯一原因，也没有实现或采纳这个候选。
2. **把尺寸变化作为单独契约。** 48pt 对照证明尺寸与可见密度策略有实际影响；正式
   方案仍须兼顾信息密度、待处理提示、hover/focus、键盘与可访问性。不要仅凭这一组
   毫秒数永久加高所有行。
3. **保留现有 Observation、Swift Concurrency、SwiftUI/AppKit。** 若稳定分区投影仍
   无收益，再对相同交互做 AppKit 列表原型。当前热点是目录的图更新和布局，没有
   TCA/SwiftData 迁移或更多缓存的直接性能依据。

## 复现、来源与验证

```sh
scripts/build-native-acceptance.sh
python3 scripts/run-native-acceptance.py --mode sidebar-layout-content --app <固定应用> --output <新目录>
```

其他后缀为 `noop`、`order`、`pins`、`height`、`height-fixed`。无采样各三轮，按不同
顺序串行执行，没有与本任务的编译或 profiler 并行；其他桌面进程不受控制。
延迟包含至少 1ms 的异步等待、布局/显示/CA flush 和探针核验。数组构造与详细几何
统计在响应样本外，在循环 CPU 内。无变化控制的 2.20ms 是这套就绪检查的底数，
不能直接从其他样本相减得到纯业务耗时。

行探针本身也有成本；这些是带探针的局部实验，不能当作正式应用每次点击的延迟。
原始记录和固定应用在 `.local/sidebar-layout/`。逐轮样本、几何、CPU、编译器、
源码/二进制摘要和失败采样见 [measurements.json](measurements.json)。构建清单中的
commit 为父提交 `2259f98`；最终源码与固定诊断应用的摘要一致。

最终 8 条回归命令全部通过：原生 all、sidebar-invalidation、invalidation，生产构建
和签名、WorkbenchChecks、ConnectionChecks，以及 19 项测量工具测试。结果记录
于 measurements.json 的 checks。本轮不覆盖真实 SSH、
模型、硬件输入/输入法、显示器延迟或长期真实使用的 FPS；未推送或部署。

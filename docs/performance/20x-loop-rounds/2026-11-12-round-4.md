## 假设

历史 switching 合成耗时约 80ms，远大于 round 3 的模型微基准。先隔离目录刷新和
会话切换，确认剩余时间在模型投影还是界面/框架，不把 Linux 的 Foundation 剖面
自动映射为 Mac 的产品瓶颈。

## 独立场景（三个进程轮次 × 每场景 80 步）

命令入口 `run-native-acceptance.py --mode <mode> --output <unique>`，三轮各运行：

| 场景 | 变更 | 轮间中位数 | 轮间 spread | 各轮 p95 |
| --- | --- | --- | --- | --- |
| render-switching | 仅选择会话及草稿；固定目录 | 66.04 ms | 3.16% | 76.09 / 77.78 / 76.39 ms |
| render-catalog | 仅目录/星标更新；固定会话及草稿 | 19.89 ms | 2.13% | 24.09 / 23.16 / 24.61 ms |
| render-combined | 两者同时 | 76.01 ms | 1.28% | 88.20 / 88.07 / 88.59 ms |

九个无捕获进程均行为通过：当前目录投影、选中会话的挂载消息、可见草稿都正确。
时钟从模型变更前开始，到 fixture 的 `settle` 确认挂载状态；包含 async 等待及主动
`layoutSubtreeIfNeeded/displayIfNeeded/CATransaction.flush`，不是输入事件延迟或 FPS。
三个场景不可以简单相减/相加分配成本，框架能合并更新。

## CPU 归因（额外一次捕获，独立于无捕获基线）

`--mode render-combined --capture cpu`：行为通过，Time Profiler 与 Points of Interest
schema/export 齐全。CPU 捕获 run 的中位数 79.01ms 不混入无捕获三轮。
只截取 `RenderIsolation` signpost 的 **3.321955083–9.718129541 s** 区间：

- main sampled CPU：6,312 ms（采样权重，不是各步 wall latency）。
- 框架剩余 graph：2,580 ms（40.9%）；框架剩余 layout：1,036 ms（16.4%）。
- row_measure：553 ms（8.8%）；transcript_other：538 ms（8.5%）。
- sidebar：247 ms（3.9%）；composer：228 ms（3.6%）。
- row_create：38 ms（0.6%）；other：1,092 ms（17.3%）。

这些是按首次匹配栈上下文划分的互斥 bucket，不是框架异步工作的最终业务归属。
`ConversationPresentationModel.update` **inclusive** 采样仅 20ms（~0.3%），
另有 `ConversationPresentationHandle.update` 22ms，二者嵌套不能相加，也不代表全部 Core。
不能将所有 `other` 或框架残余归为某个具体功能，尚不能解释历史真会话 1.3–1.6s 卡顿。

`os-signpost.xml` export 返回多个同 schema 表，RenderIsolation Begin/End 重复出现；
用相同唯一时间对确定区间，未将重复表当成多个工作负载。Time Profiler export 只有
一个数据表。初版 `--after 2` 的宽区间含启动/收尾，已用上述精确 signpost 区间取代。

## 结论与接续

合成切换仍以框架图更新/布局和挂载成本为主，现有模型缓存已让重复投影很便宜。
这一 fixture 下继续微调摘要，不能据此期待切换 20x。保留 `Sources/AgentWorkbench`
不改的红线，本轮不触碰界面布局/挂载实现，也不拿归因报告冒充优化。

下一个纯 Core 候选：`SessionEditStats.lines` 的逐 UTF-8 byte String.Index 推进。
先在 Mac 活动派生基准中剖析，再尝试 contiguous byte buffer 扫描；Character 的 LF/CRLF
边界和 canonical equality 必须与原算法对照，非 contiguous 字符串保留原路径。
这是单独的统计派生场景，不宣称解决本轮界面切换大头。

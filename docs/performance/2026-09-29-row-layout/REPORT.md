# 正文内容与视口布局的更新边界

本轮分离正文内容协调和视口布局，减少无关更新。固定离线场景中，三轮切换中位数
的中位数由 73.86ms 变为 72.81ms，约降低 1.4%；这是小幅变化，不是流畅度保证。
行宿主的首次渲染和测量仍是后续要调查的成本。

## 实现

- `ConversationDocumentLayout` 保存视图生命周期内的几何位置，通过弱引用通知
  AppKit 文档。位置变化不再写回正文的 SwiftUI `@State`，销毁时解除文档引用。
- 托管边界显式携带不可变展示快照身份、外部摘要映射、API 身份和会话/阅读作用域。
  视口更新可快速判断内容是否变化；外部摘要独立于快照身份，后来到达仍会更新行。
- 内容不变时保留索引、几何和已测量尺寸。同 ID 修改只更新对应行，屏幕外修改
  不会仅因数据变化而强制重测当前可见范围。
- 会话或行结构变化重建几何；外观、宽度、展开状态和异步尺寸变化继续走各自的
  失效与阅读锚点路径。AppKit frame 只在值改变时写入。

没有增加跨会话行宿主缓存。现有展示模型缓存和附近行保留预算保持原有策略。

## 正反向验收

挂载文档重放 40 次不变输入，内容协调、几何重建、宿主测量均为 0。相反，可见行
同 ID 修改会清除旧尺寸，外观变化会清除测量，插入/删除会更新索引。屏幕外修改
保留可见范围；同一个展示快照上的新外部摘要也通过了更新检查。
这些检查已加入现有 native `all` 模式，不依赖绝对毫秒门槛。

## 相同条件下的三轮切换对照

Apple M4、16 GiB、macOS 27.0（26A428），Swift 6.4、release -O，1280×820。
每轮基线→候选，串行重复三轮，无本任务的并行编译或 profiler；其他桌面进程
不受控制。每次使用 500 条目录、200 轮正文、八个驻留会话，进行 80 次切换，
同时改变目录状态、顺序及收藏区。计时终点检查对应正文与草稿已挂载。

| 指标 | 基线 | 候选 |
| --- | ---: | ---: |
| 三轮中位数的中位数 | 73.86ms | 72.81ms |
| 三轮中位数范围 | 73.51–75.48ms | 72.39–72.88ms |
| 三轮 p95 范围 | 81.43–85.77ms | 78.92–81.97ms |
| 滚动后静置 RSS 范围 | 220.89–221.44 MiB | 220.66–222.95 MiB |

候选每轮收到 237 次文档配置调用，其中 79 次需要内容协调；其余 158 次跳过内容
协调。仍创建并测量 316 个行宿主。该计数描述候选的实际工作量，不能把跳过比例
直接换算成整体响应速度提升。行协调和宿主测量计时是嵌套阶段，不能相加。

## 独立 CPU 采样

新旧各采样一次，用 `CatalogSwitching` signpost 限定区间，排除启动、空闲和滚动。

| 主线程采样权重 | 基线 | 候选 |
| --- | ---: | ---: |
| 整个切换区间 | 5872ms | 5823ms |
| `AG::Graph::UpdateStack::update` inclusive | 3097ms | 3070ms |
| `NSView._layoutSubtreeWithOldSize` inclusive | 2335ms | 2287ms |
| `ConversationDocumentView.configure` inclusive | 541ms | 512ms |
| `ConversationDocumentView.refreshVisibleRows` inclusive | 513ms | 517ms |
| `ConversationEntryController.measure` inclusive | 467ms | 459ms |

这些 inclusive 权重重叠，不能相加，也不是独占耗时或 FPS。单次采样只支持定位；
首次测量的主要成本仍然存在。本轮建立更精确的更新边界，没有消除 SwiftUI/AppKit
创建和布局新行的成本。

## 持续更新、输入和内存

新旧各一次 120 秒持续更新均完成 296 次更新、18 次切换，草稿、锚点和保留数量
检查通过。30/60/90 秒 RSS：基线 187.22/189.94/188.09 MiB，候选
187.17/189.14/192.13 MiB；滚动后静置为 195.58/200.16 MiB。候选静置内存略高，
本次数据不能说明长期内存收益或无泄漏；mounted 为 3–4、retained 为 4–6，
未触及现有保留上限。

单次持续更新的进程 CPU 为 12.41/11.92s，刷新到布局中位数为 26.87/25.57ms。
CPU 包含 fixture JSON 序列化，单次数据不作为真实流式性能提升的证明。

原生及 Kimi 各一次挂载输入验收通过，各 24 次中文组字循环：流式更新不覆盖组字，
提交草稿、Return 归属正确，普通输入和提交期间阅读区重算为 0，锚点偏移为 0。此处只作为
功能回归，未用单轮输入计时宣称延迟变化。

生产构建、WorkbenchChecks、ConnectionChecks、宿主生命周期及 18 项 Python
测量工具检查通过。native 的 12 种场景通过。导航预览的 reading、interactions、

## 复现和证据

- `scripts/build-native-acceptance.sh`，用 `--app` 指向保存的固定应用。
- `scripts/run-native-acceptance.py --mode switching --app <应用> --output <新目录>`，新旧交替三轮。
- 持续更新使用 `--mode joint --seconds 120`；单独 CPU 采样使用 `--mode switching --capture cpu`。
- 用 signpost 定位区间，再给 `summarize-time-profile.py` 传入 `--after` / `--before`。

基线源码摘要已验证与 `100e603` 一致；复用二进制清单里的父提交字段为 `2809890`。
候选基于 `100e603` 加本轮修改，精确源码/二进制摘要、逐轮统计、验收回执和 CPU
采样摘要在 [measurements.json](measurements.json)。完整记录位于本工作树
`.local/row-layout-final/`，基线应用在 `.local/row-layout/Baseline.app`。

仅用完整数组相等判断的早期实验没有显示稳定切换改善，其记录留在
`.local/row-layout/`，不混入以上最终候选统计。最终实现使用完整托管输入标识，
并将几何位置通知独立于 SwiftUI 正文数据更新。

这些是本机离线、程序化挂载交互结果，不覆盖真实 SSH、模型、硬件键盘、真实输入法
候选框、显示延迟或 FPS。

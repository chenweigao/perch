# 稳定的原生会话详情宿主

这次实现把加载状态与原生详情渲染树的生命周期分开。同一连接内切换会话时保留
滚动容器和 AppKit 文档，输入框及会话交互状态仍独立重建。快速切换压力场景结束后
RSS 降低约 20 MiB；没有测得一致的响应或 CPU 改善，联合场景反而略慢。
因此保留为本地可审阅的有界改动，不把它视为解决主要布局瓶颈的证据，也不扩大到
Kimi、跨会话行宿主缓存或新的框架迁移。

[上一轮诊断](../2026-09-29-render-isolation/REPORT.md) 中“响应或 CPU 有稳定收益”的
推广条件尚未满足。本轮发现的是另一项收益——快速切换后的内存占用下降；这是
不同指标，不能替代原条件。后续仍优先缩小目录 selection、单行状态和分区结构的
更新范围，继续以三个独立场景做对照。

## 生命周期与正确性

- `snapshot` 继续代表当前已读取的数据，选中另一会话时立即清空，取消及 generation
  检查照常生效。`presentationSnapshot` 只保留最后一个已加载值，用于维持视图身份。
- 加载/失败时，旧详情隐藏、禁用并从可访问性树移除。AppKit 文档先保存阅读位置，
  然后暂停协调、测量和导航；新数据准备好后恢复。直接向整棵旧行树传递 disabled
  外观会触发额外工作，因此暂停是显式的渲染生命周期操作。
- 滚动容器和文档只在同一连接内复用；详情根按连接对象区分身份。composer、活动栏、
  待发送编辑器和交互状态按会话区分，发送/停止及异步回调校验当前选择。
- 没有增加多会话 UI 树缓存或展示模型缓存预算；移除选择会释放保留值。两个连接即使
  使用同一个原始会话 ID，也不能共享组字、草稿或撤销状态。

`detail-lifecycle` 使用真实挂载控件，覆盖延迟读取、隐藏的原生视图、宿主身份、
输入框替换、组字/撤销隔离、焦点恢复、旧发送回调、暂停中的导航、返回阅读锚点、
失败重试，以及两个连接同名会话的切换。ConnectionChecks 另验迟到的 A-B-A 响应和
移除选择。该探针仅在生命周期验收模式挂载，不进入性能对照场景。

## 最终源码 A/B

Apple M4、16 GiB、macOS 27、Swift 6.4、release -O，窗口 1280×820。
基线为 `21fbf7a` 的固定应用；候选为本轮最终源码的固定应用。两者都有原有编译期
阶段计数。三轮共 18 次无 profiler 的独立进程运行：第一、三轮依次切换/目录/联合，
每组先基线后候选；第二轮反序且先候选后基线。没有与本任务的编译、采样并行，
其他桌面进程不受控制。

每次运行 80 步，目录有 500 条数据、最多显示 20 条最近会话；目录变化场景交替
显示 0/4 条置顶。八个驻留会话各有 200 轮历史。耗时起点在模型修改前，终点在
layout/display/CA flush 后确认侧边栏、正文与草稿正确。fixture 数组构造不计入每步
延迟，但计入整个循环的进程 CPU。RSS 在随后 120 步滚动并等待回收后记录。

表中数值为三轮中位数的中位数；CPU 为三轮循环 CPU 的中位数；RSS 为三轮结束值
的中位数。延迟、CPU 和内存的统计范围不同。

| 场景 | 基线 → 候选耗时 | 变化 | 循环 CPU | 结束 RSS |
| --- | ---: | ---: | ---: | ---: |
| 固定目录切换会话 | 54.20 → 53.01ms | −2.2% | 4.494 → 4.526s | 218.69 → 198.45 MiB |
| 固定会话刷新目录 | 25.34 → 25.07ms | −1.1% | 2.019 → 2.014s | 191.05 → 190.64 MiB |
| 同时切换和刷新目录 | 73.22 → 74.13ms | +1.2% | 6.053 → 6.157s | 223.05 → 203.25 MiB |

纯切换各轮中位数：基线 53.08–55.61ms，候选 52.53–54.87ms；联合场景分别为
72.11–74.07ms、73.67–74.52ms。纯切换的约 1.19ms 变化不能支持广泛的流畅度结论；
联合场景 CPU 增加约 1.7%。相较之下，快速切换结束后的 RSS 差异较一致：纯切换
基线 218.30–221.09 MiB，候选 198.03–198.58 MiB；联合场景 222.12–223.48 MiB
降至 203.17–203.63 MiB。固定会话的目录场景基本不变。

## 首次行测量与成本转移

纯切换及联合场景的每轮计数一致：

| 阶段 | 基线 | 候选 |
| --- | ---: | ---: |
| 文档 configure | 240 | 160 |
| 内容 reconcile | 80 | 80 |
| 行宿主创建 / 首次测量 | 320 / 320 | 250 / 250 |
| 行宿主重新挂载 | 320 | 0 |
| 已测行重新测量 | 0 | 0 |

纯切换首次测量总时间从 481.62–511.93ms 变为 456.16–482.10ms，远小于总切换成本。
同时 reconcile 阶段从约 14ms 增至 102–108ms：保留的文档现在在这里移除旧会话行、
退休宿主并重建几何；基线的旧文档清理发生在 dismantle 路径。阶段归属已改变，不能
仅凭某个次数下降宣称对应 CPU 同比例下降，嵌套阶段时间也不能相加。

这些结果支持减少宿主生命周期抖动，但没有推翻上一轮“主要剩余工作仍在框架更新
与布局”的诊断。本轮未重新采集 CPU 栈，因此不对剩余成本做新的控件级百分比归因。
Observation + Swift Concurrency + SwiftUI/AppKit 继续满足当前边界；此次没有提供
引入 TCA、SwiftData 或扩大缓存的性能证据。

## 持续更新与回归

另跑一对 60 秒、2.5Hz 的持续更新：双方均完成 148 次更新和 8 次切换。基线/候选
更新到布局中位数为 25.44/25.51ms，草稿更新到布局为 6.82/7.12ms；进程 CPU
为 5.848/5.583s。30 秒 RSS 为 187.39/185.38 MiB，后续滚动并回收后为
191.72/192.70 MiB。只有一对样本，不能用其 CPU 差异声称稳定收益；这个场景没有
呈现快速切换后的约 20 MiB 内存差异，不能把该收益外推到持续使用。

最终 21 条验证命令全部通过，结果写入 measurements.json 的 checks；仅退出码 0
计为通过。另有 18 次渲染对照及独立的 detail-lifecycle 验收通过。验收包括
生产构建和签名、WorkbenchChecks/ConnectionChecks、19 项测量工具检查、连接
生命周期、composer、滚动跟随，以及 reading/interactions/roundtrip/anchor 导航。
原生 all/switching/paging/invalidation/input/kimi-input 均使用最终固定候选应用。
其中 40 次草稿修改仍为 0 次阅读区重算，流式内容正向刷新有效；两种输入 fixture
各 24 轮组字，阅读锚点最大漂移均为 0。输入模式此处用于功能回归，不做延迟 A/B。

回归过程中修复了滚动跟随独立编译脚本漏列 `ConversationPresentationEnvironment`
的依赖清单；未改变其断言。此前原型及中间构建的测量没有并入最终统计。

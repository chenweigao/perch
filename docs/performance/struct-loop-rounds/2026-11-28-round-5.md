## 1. 方法与中立性

两棵 Mac 工作树同处 `origin/main = 0f56bd92`（Linux/Mac 两侧 `git fetch` 后复核一致、无漂移），
仅 tests-only harness 补丁不同，各自就地运行自己的构建产物（沿用 round-2/4 先例：
二进制副本在别处 exec 会被 SIGKILL）：

- **base** = harness **v2**，与产出 175.475ms 的 harness **逐字节相同**；
- **probe** = 在 v2 上逐轮叠加 v4→v10。

8 个作业、**49 次运行全部 `status=passed`**。所有作业脚本的守卫（补丁 sha、HEAD、逐树 porcelain）
**先于** EXIT trap 安装——修正 round-4 评审点过的「trap 先装、拒跑时也会执行 checkout」。

**中立性（4 个交替作业 × 5 对 = 20 对）**：

| 作业 | probe | base 中位 | probe 中位 | 配对差中位 | 负向对数 | **该作业 base 带宽** |
| --- | --- | --- | --- | --- | --- | --- |
| 5a | v4 | 172.344ms | 165.057ms | **−1.4455%** | 5/5 | **4.94%**（166.359–174.878） |
| 5b | v5 | 168.080ms | 168.279ms | **+1.7497%** | 2/5 | **2.19%**（165.068–168.743） |
| 5c | v6 | 169.392ms | 166.250ms | **−1.5803%** | 4/5 | **5.83%**（165.716–175.597） |
| 5d | v7 | 168.380ms | 168.650ms | **+0.1672%** | 2/5 | **8.90%**（161.720–176.704） |

**判定（已按 review run 1 B1 收窄）**：四个作业的配对差中位落在 **−1.5803% … +1.7497%**，
**符号不一致**（5a/5c 为负、5b/5d 为正），负向对数 5/5、2/5、4/5、2/5。
据此**只能**得出：**本批未检出方向一致的探针抬升**。

**不得**据此声称「探针中立性已证明」，理由有二：
1. 带宽是**逐作业**的（4.94% / 2.19% / 5.83% / 8.90%），本页初版把 4.94% 当成四个作业共同的带宽，
   属抄写与泛化错误。5b 的带宽只有 2.19%，而它的配对差中位是 +1.7497%——**同一量级**，
   所以「差值小于带宽」在 5b 上几乎没有鉴别力。
2. `(max−min)/median` 是本循环的**采纳标尺**，不是计时误差界，
   也不能反过来充当「中立性证明」（round-4 评审 B3 已就同一错误做过裁定）。

**跨作业绝对值不可互换**（base 中位在 168.08–172.34ms 间漂移）。**估计量的准确表述（评审 run 2 F4）**：每个原始份额都在**其所属的那一个窗口/轮次内部**计算，再按**明确标注的样本集**（哪个作业、n 为多少）汇总；**不同作业的数字不得混在同一个统计量里**（初版把 v4 的 9.093072%（n=15）与 5f 标度作业的 15.184ms（n=3）无作业标签地并列，见 §4.1 已更正）；
probe 变体的中位（165.1–168.7ms）与采纳值 175.475ms **同档可比但不等同**。

## 3. 窗口内成本的分项，与**不能**说什么

### 3.1 产品自带分桶的局限，以及一份派生分析器

`scripts/summarize-time-profile.py` 的 `stack_context` 规则表**不含** `ConversationTranscript.`、
`ConversationPresentationModel.`、`ToolVisibilityProjection.`、`ConversationTimelineEntry.`，
所以本轮最大的应用帧（`body.getter` 28.0ms）被整块归进 `framework_graph_remaining`。
**只看该脚本的分桶表会得出「~56ms 是框架、无法归因」并止步**——这是错的。

为拆开它，本轮写了一份**派生分析器**（`_evidence/…/round5-attribution-20261128/refine-partition.py`，
非仓内脚本、不修改产品），扩展规则表并保持同样的「首个匹配获胜」语义与同样的加权口径。
**规则顺序本身是结论的一部分**：`transcript_body` 排在 `projection_model` 之前，
所以 `transcript_body` 桶**包含**它调用的投影工作。**实测换序结果（评审 run 2 F2 更正）**：仅交换 `transcript_body` 与 `projection_model` 两条规则、其余不变，六窗中位为 **`transcript_body` 4.0ms / `projection_model` 25.0ms**（脚本副本与 6 份原始输出归档于 `refine-partition-ruleorder-check/`）。初版写的「约 19ms 与约 10ms」是**照 inclusive 值推算的（28−18=10、18≈19）、从未实测，已撤回**；差异原因是 `projection_model` 的规则集**不止** `ConversationPresentationModel.` / `ConversationPresentationHandle.`，还含 `ToolVisibilityProjection.`、`ConversationTimelineEntry.`、`ConversationTimeline`、`ConversationProjection`、`ConversationSearch`，换序后它把 `body` 内涉及这些符号的样本（含 `ConversationTimelineEntry.id.getter`）先抢走。**`presentation.update` 的 inclusive 值 18.0ms ≠ `projection_model` 桶**：前者是一个具体函数的 inclusive 权重，后者是一组前缀规则的首个命中桶。

### 3.2 残量的准确表述（review run 1 B4 更正）

初版两处**过度归因**，现予撤回：

1. ~~「剩下的 ~150ms 是主 actor 上的延迟工作」~~ —— 超出证据。
   `poll_sleep_ms` 只证明 harness 任务在那段时间**被挂起**；
   挂起期间主 actor 可能在跑产品工作，也可能在等调度、等显示管线、等锁。
   本轮**无法区分**，故只能说：**挂起时长是「产品按自己节奏完成的工作」的上界**。
   这与「≈36% 窗口时间主线程未被采样」并不矛盾——后者本身就说明窗口不是纯 CPU-bound。
2. ~~「~62ms 主线程 CPU 是不含应用符号的纯框架栈」~~ —— **不成立**。
   逐窗扣除 `body`+`configure` 后的残量为 **67 / 63 / 61 / 70 / 62 / 56ms（中位 62.5ms）**，
   其中仍含具名应用栈：`sidebar` 4.0ms、`composer` 3.0ms、`transcript_document` 里
   `configure` 之外的部分、`stdlib_string_collections` 2.5ms，以及 `projection_model`（**补零后 0.0ms**；该桶仅 1/6 窗口出现、出现时 1.0ms——评审 run 2 F1：初版把「桶出现时的条件中位」当成了「全窗口中位」），
   以及评审独立指出的文档异步 retire 与 `NativeAcceptanceRunner` 帧。
   准确表述是：**这 62.5ms 是「未被 `body` 与 `configure` 这两条已具名分支覆盖」的主线程 CPU**。其中 `framework_graph` + `framework_layout` + `framework_other` 三桶（单窗口内互斥）**逐窗求和后再取中位 = 50.0ms**（逐窗 52/50/47/57/50/46ms；占主线程 CPU 逐窗份额中位 **47.0238%**、中位数之比 47.62%）。**估计量更正（评审 run 2 F3）**：初版「约 51.5ms」是三个桶**中位数的直接相加**（28.0+12.5+11.0），而中位数之和 ≠ 和的中位数。**措辞更正（同条）**：这三桶**不得**称「栈上无应用符号」——分桶只检查**有限前缀是否命中**，并未检查栈上不存在其他应用符号；实测反例：`timeprofile/run-alt1/r1` 的 `framework_graph` 桶内有 **1.0ms** 的 `NativeAgentView.bottomBar` 路径（**该值经本执行器自行从归档 `time-profile.xml` 重算**，复算脚本与输出为 `verify-bottombar-claim.py` / `.json`；评审 run 2 的 F3 写的是 3ms，本执行器未能复现该数值，故采用自算的 1.0ms 并在此披露差异。**定性结论不受影响**：规则表之外的应用帧确实落在 `framework_graph` 桶内），归档样例栈也直接显示应用帧与 AG 帧共栈。准确表述是「**未命中预列应用规则的残差桶**」。其余部分仍带应用符号但本轮未进一步归因。

同理，**≈36.5% 的窗口时间主线程未被采样**，采样排除等待中的线程，
故这段时间**既不能记为空闲、也不能记为产品工作**，本轮不归因。

### 3.3 采样与 inclusive 的口径

- inclusive 栈权重互相重叠，**不得相加为总量**。哪一对可加由**归档样例栈的帧序**决定：
  评审已独立核查六窗原始样本，`presentation.update` 出现在 `body.getter` 之外的权重为 **0**（父子成立），
  `body.getter` 与 `configure` 同栈交叠权重为 **0**（兄弟成立，可相加）。
- 初版曾把二者并列写成「应用代码（body 28ms **+** update 18ms）」，那是**嵌套成本的加法表达**，
  已更正为「`body` 28.0ms，其中**包含** `presentation.update` 18.0ms」。
  可相加的是兄弟分支：`body` 28.0 + `configure` 15.0 = **43.0ms**
  = 逐窗份额中位 **25.439266% 的窗口** / 约 41% 的主线程 CPU。
- `specialized Collection.map<A, B>(_:)` 在窗口内有 15.0ms，但**不归因**：
  同名符号既出现在 body 的 `rows.map` 路径，也出现在 Auto Layout 的
  `ViewLeafView.sizeThatFits` / `AppKitPlatformViewHost.intrinsicLayoutTraits` 路径
  （归档样例栈恰好是后者），而 `app_stack_examples` 每个名字只保留一个样例。
- 采样捕获下的 mount 值只作归因用，**不作性能数字**；中性数字来自 §1 的交替作业。
  （核对：捕获下窗口 156.734–176.404ms，与中立运行 165.1–168.7ms 同量级。）
- **消融不是固定场景**：catalog=8 的运行不得被引用为冷首访数字。

## 4. 裁决

### 4.1 更正终态一处论断

INDEX「循环终态（2026-11-28）」节与 round-2 详情页曾写「挂载另含约 165ms 视图/布局，shard A 不触及」。
**该论断两处都错**：

- 不是「视图/布局」：转录文档路径（`document_configure`，内含 reconcile、可见行刷新、行几何、
  host 创建、文本测量）——**两个作业分别标注**：**v4 作业（n=15 轮）：15.346083ms / 逐轮份额中位 9.093072%**；**5f 标度作业 8000 turns 档（n=3 轮）：15.18425ms / 8.997656%**；冷挂载**只物化 3 行**；
  `row_create` 桶 1–3ms；细化 `framework_layout` 在三档规模上持平（12/12/12ms）；
  harness 自己的 layout/display/CA flush 全窗仅 **1.576ms**，收尾 flush **0.010667ms**。
- 不是「另含」：`model.open` 同步段只有 **0.132958ms（逐轮份额中位 0.079524%）**，
  模型层工作被 Observation 推迟进**同一个**窗口，与视图工作交织在同一段轮询里。

「两个倍率不可相乘」「不得把模型层倍率当整窗交互倍率」这两条**结论不变**，变的只是理由。
这也解释了为什么模型层 2.117× 只换来整窗 1.15×。

### 4.2 立项提议「mounted 路径的视图/布局优化」→ **本轮不立项**

依据即 §4.1 与 §2 第 1/5 刀。

**结论强度（review run 1 B6 要求收窄）**：本轮建立的是
「**在该固定场景下，行级视图/布局路径未表现出可攻的净下界**」——
文档路径 8–9%、只物化 3 行、框架布局不随规模增长。
这**不等于**「该方向已被否证」：本轮没有对任何视图/布局候选做过 A/B，
`framework_layout` 12.5ms 与 `framework_other` 11.0ms 也未被进一步归因，
细化分桶的残差桶（`stdlib_string_collections`、`framework_other`）只指认**首个命中的规则类别**（脚本是「首个匹配获胜」，**并非按帧深度选桶**）、不指认调用方。
按本循环既有纪律（筛选通过 ≠ 净下界成立；相位上限 ≠ 可转化份额），
**记为「本轮未建立可攻净下界，不立项」，而非「已否证」**。

> **编号更正**：本轮初稿把该提议写成新队列项 ⑥，与仓内**既有** ⑥（`sameNavigation`
> 共享连续存储短路，round-2 评审 N4 登记）**撞号**。被裁决的是一项**本轮提出的立项提议**，
> 不是任何既有队列项；新项编号为 **⑦**。既有 ⑥ 处置**不变**（评审已逐字节核对 ①–⑥ 行未改动）。

### 4.3 新队列项 ⑦ — `ConversationTranscript.body` 的 O(turns) 投影与视图模型构造

**状态：立项为「待证明候选」，不记为可采纳收益。**

- **已测上界**：`body.getter` inclusive **28.0ms** = 逐窗份额中位 **16.67607%** 的窗口 /
  **26.314103%** 的主线程 CPU；其**内含** `presentation.update` 18.0ms，
  故属于 body 自己的部分约 **10ms ≈ 窗口 5.9%**，高于本循环 **2.5%** 的同场景入口门槛——
  **但这是上界，不是净下界**。
- **规模证据的强度限定（review run 1 B5 更正）**：本轮能主张的是
  **(i)** 在这三档夹具上 `body.getter` 的 CPU 观测近似随 turns 增长（4 → 7 → 28ms，端点 ×7.0、指数 0.936），
  **(ii)** 源码确认 `body` 对全部行做 O(rows) 遍历并逐行构造视图模型（`:377`）。
  初版据端点指数 0.31（细化前的 `framework_graph` 桶）判定 AG 成本「不按文档行数付费」并排除每行工作，
  **推理过强、已撤回**：一个「固定成本 + 线性项」的模型 `24.429 + 0.003571 × turns`
  同样给出约 28 / 31.6 / 53ms，与观测的 28 / 32 / 53ms 贴合。
  该反例**不是**本轮认证的新模型，只说明端点指数**不足以完成排除**。
  三档实验也没有控制或拆分 RSS、内存压力、AttributeGraph 节点规模、`body` 求值次数等替代解释。
- **catalog 消融的强度限定（review run 1 B6 更正）**：本轮能主张的是
  「**这三次捕获中，把 catalog 从 500 缩到 8 后，窗口中位与 `framework_graph` 中位均未观察到明显下降**
  （窗口 168.286 / 172.060 / 167.988ms，`body.getter` 三次都 28.0ms）」。
  初版据此写的「500 会话侧栏总共只值 2–5ms」是**总成本上界**、「不是驱动方」是**因果排除**，
  **两者都超出证据、已撤回**：两端控制的中位差 0.18% 不是噪声界；
  三档各自 3 个 mount 样本的全距/中位约 **7.26% / 8.10% / 13.38%**，且每档只有**一次进程捕获**；
  符号化的 `sidebar` 桶也**不能界定**所有延迟框架工作中的侧栏成本。
- **入口判据未满足**，故只立项不采纳：
  1. **CPU 份额 ≠ 窗口份额。** 8000 turns 下主线程只有 **63.456445%** on-CPU
     （1000 turns 下 94.74%），窗口并非纯 CPU-bound；另有 **36.543555%** 未被采样、不可归因。
     省掉 28ms CPU **不等于**窗口少 28ms。收益**只认** `struct_cold_mount_ms` 的同机交替 A/B。
  2. `presentation.update` 18.0ms 属**模型层**，与 round-2/4 的模型层基准
     （`update_wall_ms` 31–35ms、`make_total_ms` 14.9ms @16k）**口径不同，不得等同或相加**。
  3. 惰性化 `contents` = shard B 方向，须先满足 `shardB-A2-design.md` §11.4 的复活条件；
     `ConversationTimelineEntry.id` 是锚点 / 折叠 / 阅读位置的键，改其语义碰红线。
- **推进顺序（写死，避免下次再议）**：
  - (a) **先做不改语义的子项**：把 body 内每行 3 次 `entry.id` 计算属性访问降为 1 次（或缓存），
    单独在**窗口口径**上做 A/B——按 INDEX「机制继承」与 TASK 的规定，
    正式采纳证据需**同机交替 ≥6 对**、逐对差超带、并披露延期成本。
    （初版写「≥5 对」，低于既定门槛，已按 review run 1 B11 更正为 **≥6 对**；
    本轮的 5 对只用于**探针中立性前测**，不能充当正式采纳证据。）
  - (b) 若要动 `contents` 的构造时机（惰性/增量），须同时满足 §11.4 复活条件
    （行几何次线性化或 `O(n−i+k)` 线性增量 splice，且重测 C ≲0.5ms@16k 行——该 0.5ms 是设计目标值、非实证阈值）。
  - (c) 任何 ⑦ 候选**不得**引用本轮的 CPU 时间作为收益证据。
  - (d) 采纳仍须满足 §9 双边界验收（含全文滚动 A/B）与净下界严格 > 2.5%、成本搬迁完整披露。

## 6. 本轮新增方法学教训

编号**续仓外 `REPORT.md` §5 的 1–15**（即 **16–27**），在仓内 INDEX 归并为「否定清单」第 **13** 条
（review run 1 N2 更正：初版写「编号续 INDEX」，而 INDEX 原有编号只到 12）。

16. **「推断出来的数」不能写成「测出来的数」。** 本轮犯了三次同类错误：
    (i) 终稿把另一基准的模型层成本当作本窗口内的成本（§4.1）；
    (ii) 把另一个夹具的 `actual_messages=18667` 当成本夹具的行数（§开头规模口径，评审 run 1 B7）；
    (iii) 把「细化分桶换序后约为 19ms / 10ms」写进五处文档，而那是照 inclusive 值推算的
    （28−18=10、18≈19）、**从未跑过换序**；实测换序是 **4.0ms / 25.0ms**（评审 run 2 F2）。
    规则顺序敏感性这类「换个参数会怎样」的说法，**必须实跑**，因为规则集的重叠程度无法凭直觉估计。
17. **harness 的轮询 sleep 属被测窗口，必须自证代价。** 若没有第 3 刀，
    「99% 在 settle 里」会被两头误读（「99% 是 harness 开销」或「99% 是产品工作」）；
    两者都不成立：harness 实付 `settle − sleep` 中位 1.615625ms（v6）/ 1.536208ms（v7），
    其余是挂起时间，而挂起时长只是产品工作的**上界**。
18. **口径声明要写进产物本身，但产物里的声明也要被审。** 见 §5。
19. **Linux 侧无 Swift 工具链 ⇒ harness 编译错误只能在 Mac 构建时暴露。**
    v8 首次上传即 rc=1（`OSSignposter` 要 `StaticString`）。作业须构建先于运行、失败即 `exit 1`、
    **被拒补丁连同原因归档而非覆盖**。
20. **分桶规则决定你能看见什么，工具默认的分组不是事实的分组。**（§3.1）
21. **同名符号跨多处出现时不能据单个样例栈归属。**（§3.3）
22. **消融要给驱动方假设一个可失败的对照，且控制组放在两端**；
    但**阴性结果只能支持「未观察到下降」，不能升级为总成本上界或因果排除**（§4.3）。
23. **inclusive 上界必须按样例栈帧序扣除嵌套部分**；哪一对可加由帧序决定，不由直觉决定（§3.3）。
24. **同名作业重投前不得删除上一次的 `results/<name>.log`。**
    本轮为「保持目录干净」在重投前 `rm -f` 了首编失败的日志，**销毁了失败证据**，
    导致评审无法独立认证该次 trap/porcelain 行为（`NOT_VERIFIED` 第 1 条）。
    正确做法是先改名归档（`<name>.attempt1.log`）再重投，且输出目录名带尝试序号。
    可从会话记录恢复的部分已逐字转录并标明缺口：
    `_evidence/…/round5-attribution-20261128/v8-first-compile-failure-RECOVERED.md`。
25. **统计量必须写明估计量，且自己写的汇总代码也要按同一标准审。** 三层错误依次暴露：
    (i)「中位数之比」与「逐窗份额的中位数」数值接近但不是同一个量，初版混用并用泛称掩盖（run 1 B2）；
    (ii) 处置 (i) 时新写的「~51.5ms」又是**三个桶中位数的直接相加**（run 2 F3）；
    (iii) 自己写的 `canonical-numbers.py` 聚合细化分桶时**缺桶未补零**，把「条件中位」当成「全窗口中位」
    （`projection_model` 报 1.0、实为 **0.0**，run 2 F1）。
    修法：份额类数字由单一脚本一次算出、脚本内显式补零并输出 `windows_where_present`；
    **但不宣称「不可能再被混淆」**（run 3 R3-B3 举出反例）。
26. **「缺席」是否等于「零」，取决于该列表是否完备。** 对 first-match 的**完备划分**，
    某窗口缺一个桶就是 0，必须补零（run 2 F1）；而对**截断的 top-N 列表**
    （归档 `main_leaf_top` 恒为 25 条，`run-alt1/r2` 实际有 87 个 leaf 名、top-25 只覆盖 104ms 中的 42ms），
    缺席**不代表零**，补零会算错。本执行器正是据此把 `_StringGuts.append` 的六窗叶权重中位
    从正确的 **1.5ms** 误「更正」为 **1.0ms**，被评审 run 3 R3-B5 挡回。
    ⇒ 引用任何 top-N 字段前先看它的截断长度；需要全量就回到原始 XML 复算。
27. **评审给的数值也要复核，不能因为「来自评审」就免检。** 本轮把评审 run 2 的「3ms `NativeAgentView.bottomBar`」
    与「`run-alt1/r1` 桶 17ms vs `configure` 14ms」直接抄进五份文档；自行从 XML 复算后分别是 **1.0ms** 与
    **错配窗口**（17ms 属于 r0/r2、14ms 属于 r1）。评审是独立**审查者**、不是本轮的**测量来源**：
    定性判断可直接采纳，具体数值必须回到本轮归档产物复算后才可写入文档。

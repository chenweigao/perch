## 改动（v1=fe17ef1 → v2=1f9b5d4；单文件 `ReplyMath.swift` + 新钉死文件）

`splitInline` 每 run 守卫 `run.text.contains("$")` →
`run.text.utf8.contains(36)`：

- **旧守卫的真实形态（复核发现 3 更正）**：`contains("$")` 在产品构建中
  绑定到 **grapheme 感知的 Foundation 子串搜索**（Mac trace：
  `StringProtocol.contains<A>` → `StringProtocol.range<A>`；评审方对
  Linux 基线二进制的反汇编同见 Foundation `range` 调用），而非
  Collection 的逐 Character 元素比较。其准入在两平台**合法分歧**：全融合
  Prepend 形态 `"\u{0600}$x\u{0600}$"` macOS 拒绝（grapheme 对齐搜索）、
  Linux corelibs 准入（搜索缺 GB9b——round-17 探针既有发现，本轮双端
  显式重载探针复核：[round-19/checks/guard-admission-probe-record.md](round-19/checks/guard-admission-probe-record.md)）。
- **等价论证（不变量口径，不依赖各平台准入细节）**：① 0x24 在 UTF-8 中
  自同步（ASCII 字节不出现在多字节序列内部），任何搜索形态命中 "$" 都
  需要该字节——字节缺失 ⇒ 一切旧守卫（两平台、两重载）都拒绝 ⇒ 新守卫
  拒绝集与旧拒绝集在字节缺失方向重合（准入为超集）。② 核心不变量：
  **凡 Characters 中无裸 "$" 的 run，split() 都是保值无操作**——while
  循环的 `text[index] == "$"` 对融合 Character 恒 false、零命中，终点
  `flushText(upTo: text.endIndex)` 返回单个 text/flags 逐字段值相等的
  run。故无论旧守卫在某平台准入与否（分歧单元格见探针记录），新旧输出
  逐平台逐位一致，**无需平台回落**。守卫其余条件（link/code/math 排除）
  不动。
- 与 round-17 normalizeDelimiters 守卫的对比：那里字节对匹配不蕴含
  Character 序列匹配（快速接受须双侧边界证明、不确定对回落原搜索）；
  这里方向相反——误纳被 split() 的保值无操作消化，等价不依赖回落。

`Sources/AgentWorkbench` 零差异；Linux 与 Darwin 走同一新代码（平台
中立）。

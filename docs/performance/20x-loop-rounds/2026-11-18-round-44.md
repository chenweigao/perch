## 方法：round-39 F3 教义落地

round-39 F3 记录「ARC/bridge 等通用叶桶是非互斥分类桶，不是可攻性分区」，round-43 的
分析器只对 hash/dict 叶做了消费方归因。本轮把它扩展到 utf16-bridge / arc-copy /
cf-match / teardown 四桶，方法是：对 decode-free 的每个样例，从叶帧向上走，跳过
**机制帧**，把样例记给第一个「真实代码」帧。

关键实现细节（两轮错误与修正，如实披露，见 `round-44/ATTRIBUTION-NOTE.md`）：

- **第一轮**：停在「第一个非桶帧」，把 60-70% 的样例记到运行时机械帧上（ARC 慢路径
  `RefCounts::doDecrementSlow`、`_ContiguousArrayBuffer._consumeAndCreateNew`、
  `_Variant.setValue`）。
- **第二轮（评审 F1）**：`frame.startswith(RUNTIME_PREFIXES)` 不处理 `specialized` /
  `static` / `outlined` 等修饰前缀，导致已列入排除集合的 `Dictionary.`、`String.`、
  `protocol witness` 等**漏过**——归档表里残留 `specialized Dictionary.subscript.setter`
  （2.53%）即为症状。修正=先剥离修饰前缀再做规则匹配，并把
  `outlined init with copy` / `consume of (` / `DefaultStringInterpolation` 等
  值复制/析构机械补入排除集；`0x…` 与 `<deduplicated_symbol>` 显式记为
  `<unresolved-system>`（1.09%），不再折进任何消费方。
- **修正后的关键变化**：`Dictionary.subscript.setter` 不再自成一类，其样本归到真实
  消费方——**`Presentation.parents` 闭包 277 样本 / 2.37%** 由此浮现；`Array.+` 由
  8.57% 校正为 **8.43%**。

- **第三轮（复核 F1）**：剥离修饰前缀的修复本身引入回归——`"outlined consume"` /
  `"specialized _ArrayBuffer"` 等**针对原始拼写**的规则在剥离后失效，
  `"consume of ("` 也匹配不到 `consume of ToolVisibilityProjection.Split?`。修正=**同时匹配
  原始名与剥离名**，并补 `_ArrayBuffer` / `consumeAndCreateNew` / `Array.init` /
  `_xzm_reclaim` / `consume of ` / `ContiguousArrayStorage` 等存储与分配机械。
  该轮影响：Array.+ 回到 8.57%、harness 主符号 8.10%、make flush 2.01%、`update` 1.99%；
  Array.+ 的第三组 `Model.update`（0.14%）随之浮现——**数值已被第四轮取代**。
- **分类器遗漏（复核 F5）**：harness 原用 `startswith("benchR43Profile")` 漏掉闭包与
  `stamp`；find-bar 原缺 `_FillNextTokenInCache`（经 `DDScanner`→`NSDataDetector`→
  `ReplyDocument.linkMatches` 通向检测器）。该轮结果为 find-bar 20.00%、harness 8.36%、
  产品 30.20%、未解析 1.09%——**已被第四轮取代**（下表为最终值）。

- **第四轮（复核 F1''/F2''/F5''）**：仍有余留机械帧被当作消费方——`UnsafeMutable
  BufferPointer.initialize`（23）、`Array._makeUniqueAndReserveCapacity…`（11）、
  `Array.reserveCapacity`（11）、`_copyCollectionToContiguousArray`（9）、
  `Sequence._copySequenceContents`（6）、`_xzm_segment_group_span_mark_used`（6）、
  `_NativeSet.resize`（3）。补全后 Array.+ 由 1002 增至 **1003/8.58%**（displayMessages
  多出 1 个经 `initializeWithCopy`→`Array.append` 的样本）。该轮数值（harness 8.50% / find-bar 20.13%）**已被第五轮取代**

  `ProtocolTests.main()` 的分类）。

- **第六轮（复核 F1''''，方法切换）**：逐条补帧名证明**不可终止**——第五轮补完仍有约 30
  个样本停在 generic collection / CF 字符串存储 / ObjC 容器 / 栈探测帧上。改为**闭集白名单**：
  消费者 = 栈上第一个属于已知产品模块、bench harness 或 find-bar 的帧；其余一律视为机械帧

  `_UnsafeBitset`、`MutableCollection<>.sort`、`xrealloc`；find-bar 另补
  `u_countChar32`、`DDCachingStringTokenizer`。该轮数值（find-bar 20.20%、harness 8.52%、
  产品 29.82%、未解析 1.11%）**已被第六轮取代**。

## 验证族统一净估复核（round-37/39 遗留队列项②）

源码复核（本轮新增证据；**按路径分口径**）：

- **历史复用路径**：`ConversationPresentation.swift:595-610`，`reuseEnd = reusedHistory
  && oldCosts.count >= split ? split : 0`。当 `reuseEnd == split` 时循环覆盖
  `[split, count)`——**最新轮整体**，不是「本次新追加段」；`canReuse` 的
  `sameWindow` 比较的是**历史前缀 `[0, split)`**。两个半开区间**严格不相交**，
  不是「边界重合」。
- **非复用路径（prepend / 历史重建 / 单轮）**：`reuseEnd = 0`，**循环范围**覆盖
  `[0, count)`；但**实际比较范围**只含存在对应旧索引（`previous.messages.indices
  .contains(index - shift)`）的消息，`shift` 只用于对齐旧索引，并不跳过旧后缀窗。
- **第三层（初稿遗漏）**：`ToolVisibilityProjection.swift:228-234` 的 `projectTurns`
  只在 `canReuse` 未成功时进入，且只有**找到旧 chunk 且 count 相等**才调
  `KimiMessage.sameWindow(source, previous.source)`；prepend 后旧 turn 若命中该条件
  会全部参与验证。

⇒ 初稿的 **≤2% 上界撤回**：它把流式复用路径的「不相交」误写成「仅重叠于新追加段」，
又用 `cost(_:)` 的 1.88%（payload 长度计算，`ConversationPresentation.swift:657-670`）
冒充整个验证族的可省上界。**现有证据不足以给出定量上界**，需按路径插桩
（复用率、`reuseEnd`/`shift` 分布、`projectTurns` turn 数）后才能裁决。本轮按
「无可采纳收益、证据不足」记录，不立项。

**方法学入册**：重叠消除的净估必须按**路径 × 每层实际扫描范围与触发条件**重算
（`reuseEnd` / `shift` / 复用率），不能用并集份额相减，也不能用同名消费者的叶份额
冒充该层的总成本；同一机制在不同路径下扫描范围可以完全不同。本轮两版表述先后被
Codex 评审与独立评审更正。

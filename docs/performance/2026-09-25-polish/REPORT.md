# Perch 集成与性能、交互整理（2026-09-25 至 09-26）

## 已实现

基于主线 27968b8，在独立 worktree 集成本机 Kimi/Codex 接入、新建任务布局；随后合入主线 9a56056 的 Kimi 标题识别修复。主 checkout 和其他 worktree 未修改。此次没有推送、部署或替换用户正在运行的 App。

- 文字草稿使用 250ms 合并窗口；附件、待发队列变化立即排入串行写入，退出同步刷新。取消旧定时保存，避免覆盖更新的已发送/退出状态。异常退出仍可能损失尚处于合并窗口的最后一小段文字。
- 空闲原生对话快照降为每两秒读取。目录保持已有 2/5 秒节奏；发送回执每周期核对，运行中、待审批、有待发消息保持快速刷新，切换立即加载。历史窗口变化使旧响应失效时，下一周期立即补读。
- 高度缓存限制为 16 个最近保存的会话；阅读位置、跟随、展开状态限制为最近 256 个会话，删除会话时清理。历史消息本身不被删除。
- 增加仅需处理事项通知、会话静音、两秒完成通知合并。单条打开会话，多条打开工作台。
- 区分本地排队、等待接收确认、已接收、执行中、接收状态待确认；补齐草稿错误和通知本地化。修复集成主线中 Recap 的 20 条缺失翻译。
- 侧栏操作热区统一为 28pt，选中底色适配深浅外观；保留外层 Liquid Glass。新建任务显示非 Kimi 附件限制。
- 同步草稿持久化、本机 Agent、模型与思考入口、轮询节奏的文档。

## 性能记录与边界

## 真实 Kimi 与双 Mac 边界

只使用 dev-env 上独立的“Perch 双端恢复验收 0925”会话及 `/tmp/perch-recovery-20260925`。运行时 Kimi 2.0.2，使用已有 LAN 模型、manual 权限模式，没有更改服务配置。

- SSH/HTTP 请求返回后客户端退出；新连接读回同一会话的完成状态及 `PERCH-RECOVERY-0925` 标记。
- 一次仅写入验收目录标记文件的调用被运行时直接允许，**没有触发审批，因此不能记为审批恢复通过**。
- AskUserQuestion 产生真实待回答卡片；断开并重新连接后，同一问题仍处于等待状态。随后读到“继续”的回答、`PERCH-QUESTION-DONE` 与 completed，待回答列表为空。尚未确认回答来自哪台 GUI 客户端。
- 对同一独立会话发起仅 sleep 30 的任务，观察 busy=true 后 POST abort，返回 aborted=true；新连接读回 busy=false、last_turn_reason=cancelled。测试脚本第一次误用 GET，返回 40401，没有执行停止；改用生产客户端的 POST 后通过。
- 初次合成提示因 SSH 参数边界只送达“这是”，该次不计为标记测试成功。改为 base64 传递参数后，完整标记测试通过。令牌只在远端内存中读取，不记录在报告中。

上述是实际 Kimi 服务协议验证，不是两台 Perch GUI 客户端的验收。MacBook 当前可远程登录 Mac mini，这不等于 MacBook 本地也运行 Perch。第二台 Perch 的独立身份、UI 观察、休眠/唤醒与停止当前轮次仍需人工确认；本次 HTTP 连接不能代替这些证据。

待配合步骤：确认刚才的“继续”是否来自 MacBook 本地运行的 Perch；再分别覆盖两个独立 Perch 客户端的运行中退出、真实审批与合盖唤醒，按 docs/RELIABILITY-ACCEPTANCE.md 记录结果。专用会话最终停在 cancelled，没有遗留运行中的测试任务或待回答卡片。

# 切换后的刷新缺行

PR #79 处理初始阅读位置就绪前的显示，但没有覆盖后续快照刷新时的可见行完整性。
在合并后的生产代码上，新的离线刷新夹具复现了部分正文消失一轮布局的情况。

## 复现与原因

夹具通过生产 Kimi HTTP 解码路径延迟 180ms 返回快照，保持消息身份不变，
交替增减实际可见的第 199 轮助手正文长度，模拟缓存正文先显示、服务器结果随后更新。
每次切换采集 60 个布局样本，覆盖冷加载、缓存切换、长短正文变化及原阅读锚点恢复。

旧实现的一次失败发生在切换后约 250ms：正文从 74,515pt 缩至 71,075pt，
AppKit 已调整滚动位置，可见区域却仅挂载第 200 轮用户消息，缺少本应可见的三行。
文档本身没有隐藏，滚动容器也未重建。后续异步 viewport 回调才补齐这些行。

这是间歇性的时序问题：新增完整性断言的同一基线二进制，四次运行中三次通过、
一次失败。初次实验修改末条正在运行的回复，没有改变可见正文，已排除为无效覆盖；
最终夹具明确断言快照版本和实际文档高度均发生变化，避免这种假阳性。

## 修复

保留 viewport 更新合并，在原生文档 `viewWillDraw` 中补齐实际可见行再绘制。
同一可见范围仍走现有快速返回；不扩大预加载、不缓存截图、不增加等待时间，
也不在刷新时重新隐藏已经显示的正文。

检查同时要求：首次显示后不能再次变空白；可见区域不缺行；无旧会话正文；
缓存切换复用容器；跟随末尾最终到达新末尾；中途阅读锚点保持不变。
内容变化可以移动末尾，因此不把刷新期间的每一个滚动偏移强制判为恒定。
新增 `kimi-refresh` 已接入 macOS functional checks。

同一生产修复的首个候选连续五轮（30 次切换）通过。结果是原生布局采样证据，
不是显示帧率，也不能据此断言任意真实会话都无闪烁。正式安装包与开发候选仍需
分别核对版本，不能由 PR 合并推断用户实际运行的是修复版。

## 复现命令

```sh
bash scripts/build-native-acceptance.sh
python3 scripts/run-native-acceptance.py --mode kimi-refresh --output .local/refresh-check
python3 scripts/run-native-acceptance.py --mode kimi-switching --output .local/switch-check
```

每次使用新目录。`results.json` 保存二进制与源码指纹、每次运行的结果及变化样本；
本机路径已改为仓库相对路径。原始报告在本地 `.local/switch-refresh/`。

## 相关回归

最终夹具增加“必须发生版本和高度变化”的断言后，`kimi-refresh`、`kimi-switching`、
`detail-lifecycle`、`kimi-invalidation`、`paging` 全部通过。导航 `reading`、
`interactions`、`anchor` 及 22 项性能工具测试通过。

一次固定二进制顺序对照（先旧后新、测量期间没有并行编译）中，200 轮完整下读
334 步的 p95 为 15.14→15.10ms，上读 333 步为 13.49→13.11ms。仅用于观察
这次绘制边界补齐是否产生明显额外开销；样本不足以声称提升性能或证明任意负载无回退。
